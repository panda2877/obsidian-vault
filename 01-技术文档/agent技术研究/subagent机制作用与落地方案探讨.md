# SubAgent 机制作用与落地方案探讨

> 日期：2026-05-08

## 一、研究背景与目的

### 1.1 研究动机

随着 Hermes Agent 体系从单体 Agent 演化为多 Agent 协作体系，subagent（子代理）机制已成为架构核心。目前体系中存在**多种 subagent 机制并存**的局面：

| 机制 | 状态 | 用途 |
|------|------|------|
| `delegate_task` | 生产中 | Agent 间单次委托 |
| Profile 多进程 | 生产中 | 独立人格 Agent（如音/思月/紫灵） |
| Kanban 分派 | 生产中 | 跨 Agent 异步任务编排 |
| ACP（Agent Communication Protocol） | 引入中 | Claude Code / Codex 外部 Agent 集成 |

目的：系统性梳理各机制的**本质区别、适用场景、协作关系**，形成一套清晰的选型指南和落地方案。

### 1.2 核心问题

1. 这些机制之间是什么关系？互相替代还是互补？
2. 什么场景该用哪个？
3. 能否统一成一个抽象层？

## 二、SubAgent 机制全景

### 2.1 什么是 SubAgent

**定义**：SubAgent 是由主 Agent（父进程/协调者）派生的、在隔离上下文中执行任务的子智能体。

**核心特征**：

| 特征 | 说明 |
|------|------|
| **上下文隔离** | 子 Agent 不共享父 Agent 的对话历史 |
| **独立推理** | 子 Agent 拥有自己的推理链路 |
| **工具可用性** | 子 Agent 可使用自己配置的工具集 |
| **结果回传** | 子 Agent 完成后将结果返回父 Agent |

### 2.2 现有机制总览

```
┌─────────────────────────────────────────────────────────┐
│                    Hermes SubAgent 生态                    │
│                                                         │
│  ┌─────────────┐  ┌──────────────┐  ┌──────────────────┐ │
│  │ delegate_task│  │ Profile 多进程│  │    Kanban 分派    │ │
│  │ (进程内委托)  │  │ (独立Gateway)  │  │ (异步编排)        │ │
│  └──────┬──────┘  └──────┬───────┘  └───────┬──────────┘ │
│         │                │                   │            │
│         ▼                ▼                   ▼            │
│  ┌─────────────────────────────────────────────────────┐  │
│  │                  ACP 外部 Agent                       │  │
│  │          (Claude Code / Codex / OpenCode)             │  │
│  └─────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

## 三、各机制深度分析

### 3.1 `delegate_task` — 进程内委托

#### 工作原理

```python
delegate_task(
    goal="你是如音，分析这个 Bug 的根因",
    context="系统日志：... 报错信息：...",
    toolsets=['terminal', 'file']    # 可限制工具集
)
```

- **进程模型**：共享父 Agent 进程
- **上下文**：完全隔离，需通过 `context` 参数传递背景信息
- **生命周期**：同步阻塞，子任务完成后才返回
- **预算限制**：50 轮对话上限
- **工具限制**：5 个工具被禁用（`delegate_task`、`clarify`、`memory`、`send_message`、`execute_code`）

#### 适用场景

| 场景 | 示例 | 理由 |
|------|------|------|
| **短期推理任务** | 分析一段代码、做技术判断 | 任务轻量，不需要长期运行 |
| **平行调研** | 同时查多个方向 | 多个 `delegate_task` 可并行 |
| **专业分工** | 银月委托如音处理技术问题 | 隔离人格，避免语气混合 |
| **一次性分析** | 审查 PR diff、搜索信息 | 结果回传后即结束 |

#### 局限性

- ❌ 不适合长时间运行的任务（受 50 轮限制）
- ❌ 不适合需要持久化的任务（进程退出后状态丢失）
- ❌ 子 Agent 不能与用户直接交互（不能 `send_message` / `clarify`）
- ❌ 不能嵌套委托（子 Agent 不能再 `delegate_task`，除非配置 `orchestrator` 角色）

### 3.2 Profile 多进程 — 独立 Gateway Agent

#### 工作原理

```
┌───────────────────────────────────────┐
│          独立 Gateway 进程              │
│                                       │
│  ~/.hermes/profiles/xingruyin/        │
│  ├── config.yaml       # 独立配置     │
│  ├── .env             # 独立凭据      │
│  ├── SOUL.md          # 独立人格      │
│  ├── MEMORY.md        # 独立记忆      │
│  ├── USER.md          # 独立用户档案   │
│  └── skills/          # 独立技能      │
│                                       │
│  PID: 1265648  | 飞书: ✅ connected   │
└───────────────────────────────────────┘
```

- **进程模型**：完全独立的 Hermes Gateway 进程
- **上下文**：完全隔离（自己的会话历史、记忆、技能）
- **生命周期**：持续运行（systemd 管理，自动重启）
- **预算限制**：无（独立进程不受 50 轮限制）
- **工具限制**：无（所有工具可用）

#### 适用场景

| 场景 | 示例 | 理由 |
|------|------|------|
| **独立人格 Agent** | 如音、思月、紫灵各自在飞书上有独立身份 | 需要长期在线、保持人格一致性 |
| **多平台接入** | 每个 Agent 独立连接飞书/微信 | 需要独立的平台凭据 |
| **长期记忆维护** | 每个 Agent 积累自己的知识库 | 记忆完全隔离，互不干扰 |
| **独立任务执行** | 紫灵持续监听需求、思月定期审计文档 | 需要后台长期运行 |

#### 局限性

- ❌ 资源消耗大（每个进程独立占用内存 + API 配额）
- ❌ 配置复杂（每个 Profile 需要独立飞书 app_id、微信 token）
- ❌ 通信成本高（Agent 间需通过飞书群聊或文件交换信息）
- ❌ 启动慢（每个 Gateway 启动需要几秒）

### 3.3 Kanban 分派 — 异步任务编排

#### 工作原理

```
┌──────────┐    kanban_create()    ┌──────────┐
│ 银月      │ ──────────────────►  │ SQLite    │
│ (协调者)   │                     │ Kanban DB │
└──────────┘                      └─────┬────┘
                                        │ dispatcher 轮询
                                        ▼
                               ┌──────────────────┐
                               │ 如音 (worker)     │
                               │ kanban_claim →    │
                               │ 执行 → kanban_    │
                               │ complete/block    │
                               └──────────────────┘
```

- **进程模型**：通过数据库解耦，任务发布者和执行者不同进程
- **上下文**：通过任务描述 + 注释线程传递
- **生命周期**：异步非阻塞，任务可跨进程、跨重启
- **依赖管理**：支持 `parents` 链，子任务等父任务完成才自动就绪
- **可观测性**：完整的任务状态、心跳、重试历史

#### 适用场景

| 场景 | 示例 | 理由 |
|------|------|------|
| **复杂工作流** | 调研→分析→撰写→审核的多阶段流程 | 依赖链自动管理 |
| **跨 Agent 协作** | 银月分派任务给如音、思月 | 异步解耦，不阻塞银月 |
| **可中断的任务** | 长时间调研、大数据处理 | 支持心跳 + 重试 |
| **需要人工介入** | 任务卡住时 `kanban_block()` 等人回复 | 支持 Human-in-the-loop |
| **审计追踪** | 所有任务历史持久化在 SQLite | 可回溯、可分析 |

#### 局限性

- ❌ 不适合实时对话（有调度延迟）
- ❌ 任务颗粒度有要求（太小的任务不值得走 Kanban）
- ❌ 需要额外的调度基础设施（dispatcher 轮询）

---

### 3.4 ACP 外部 Agent — 跨 CLI Agent 集成

#### 工作原理

```
┌──────────────────┐     ACP (stdio)     ┌──────────────────┐
│  Hermes Agent     │ ◄────────────────► │  Claude Code      │
│  (协调者)          │                    │  (子 Agent)        │
└──────────────────┘                    └──────────────────┘
         │                                      │
         │  terminal(command="claude -p ...")   │
         │  or acp_command="claude"              │
         └──────────────────────────────────────┘
```

- **进程模型**：通过 ACP（Agent Communication Protocol）或 terminal PTY 与外部 Agent 通信
- **上下文**：通过 CLI 参数 / stdin 传递
- **生命周期**：任务完成后进程退出
- **集成方式**：`delegate_task(acp_command="claude", ...)` 或 `terminal(command="claude -p ...")`

#### 适用场景

| 场景 | 示例 | 理由 |
|------|------|------|
| **外部 Agent 能力调用** | 用 Claude Code 写代码、Codex 做批量修改 | 利用外部 Agent 的独特能力 |
| **异构模型协作** | 不同模型擅长不同任务 | 可指定不同模型给不同 Agent |
| **本地能力扩展** | 用 OpenCode 做本地开发 | 利用本地 Agent 的文件系统权限 |

#### 局限性

- ❌ 依赖外部 CLI 安装
- ❌ 通信协议尚未标准化（ACP 仍在演进）
- ❌ 上下文传递有限（通过 CLI 参数有长度限制）

## 四、机制对比总表

| 维度 | `delegate_task` | Profile 多进程 | Kanban 分派 | ACP 外部 Agent |
|------|:---------------:|:--------------:|:-----------:|:--------------:|
| **进程模型** | 共享父进程 | 完全独立进程 | 数据库解耦 | 独立子进程 |
| **上下文隔离** | ✅ 隔离（传参） | ✅ 完全隔离 | ✅ 通过任务描述 | ✅ 隔离 |
| **生命周期** | 同步阻塞 | 持续运行 | 异步非阻塞 | 同步阻塞 |
| **轮数限制** | 50 轮 | 无限制 | 无限制 | 由外部 CLI 决定 |
| **工具限制** | 5 个禁用 | 无限制 | 无限制 | 由外部 CLI 决定 |
| **实时性** | 高（即时返回） | 中（需要通信） | 低（有调度延迟） | 高（即时返回） |
| **资源消耗** | 低 | 高（完整进程） | 中 | 中 |
| **持久化** | ❌ 无 | ✅ 有记忆系统 | ✅ SQLite 存储 | ❌ 无 |
| **人工介入** | ❌ 不支持 | ✅ 支持对话 | ✅ block/unblock | ❌ 不支持 |
| **配置复杂度** | 低 | 高 | 中 | 中 |
| **最佳粒度** | 秒~分钟级 | 持续在线 | 分钟~小时级 | 秒~分钟级 |

## 五、选型指南

### 5.1 决策树

```
任务来了
│
├─ 任务需要长期在线/独立人格吗？
│   └─ ✅ → Profile 多进程（如音/思月/紫灵模式）
│
├─ 任务需要异步编排/跨 Agent 协作/可中断吗？
│   └─ ✅ → Kanban 分派（多阶段工作流）
│
├─ 任务需要调用外部 Agent 的独特能力吗？
│   └─ ✅ → ACP 外部 Agent（Claude Code 写代码等）
│
├─ 任务是短期、轻量、即时返回的推理任务吗？
│   └─ ✅ → delegate_task（平行调研/专业判断）
│
└─ 任务简单到一步就能完成？
    └─ ✅ → 直接执行，不用 SubAgent
```

### 5.2 场景速查

| 需求 | 推荐机制 |
|------|---------|
| 老大问技术问题，银月需要如音回答 | `delegate_task` 召唤如音 skill |
| 如音需要独立在飞书上和老大对话 | Profile 多进程（如音独立 Gateway） |
| 银月需要协调一个「调研→分析→写文档」的工作流 | Kanban 分派（3 个任务，依赖链） |
| 需要用 Claude Code 重构某个模块 | ACP `delegate_task(acp_command="claude")` |
| 紫灵要监听用户需求并自动提出方案 | Profile 多进程（紫灵后台运行） |
| 思月要定期巡检文档和记忆文件 | Kanban（定时任务）或 Cronjob |
| 银月需要同时查多个技术方案 | 多个 `delegate_task` 并行 |
| 需要跨平台（微信→飞书）接续对话 | Profile 多进程 + session 绑定 |

### 5.3 组合使用模式

**模式一：银月 + delegate_task + 姐妹 Skill**

```
老大 → 银月 → delegate_task(如音/紫灵/思月 skill) → 返回结果 → 银月转发
```

**模式二：银月 + Kanban + Profile 姐妹**

```
老大 → 银月 → kanban_create(任务) → dispatcher 派给如音 Profile
      → 如音独立执行 → kanban_complete → 银月汇总 → 老大
```

**模式三：Profile 姐妹 + ACP 外部 Agent**

```
如音（Profile）→ delegate_task(acp_command="claude") → Claude Code 写代码
      → 返回结果 → 如音验证 → 提交
```

**模式四：全链路混合**

```
老大在飞书群发需求
    ↓
银月（主进程）接收
    ↓ delegate_task（即时判断）
紫灵（独立 Profile）分析需求 → 给出方案
    ↓ kanban_create（异步编排）
如音（独立 Profile）实现 → 思月（独立 Profile）写文档
    ↓
银月汇总 → 回复老大
```

```
│  任务发布 ↔ 任务执行 ↔ 依赖管理 ↔ 状态追踪              │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│                  ACP 外部 Agent 层                     │
│  Claude Code  |  Codex  |  OpenCode                   │
│  按需启动，任务完成后退出                                │
└─────────────────────────────────────────────────────┘
```

### 6.2 推荐落地原则

#### 原则一：分层调用，不越级

```
实时对话层  ←  Profile 多进程（姐妹独立在线）
    │
调度编排层  ←  Kanban（异步工作流）
    │
即时委托层  ←  delegate_task（轻量推理）
    │
外部集成层  ←  ACP（外部 Agent 能力）
```

上层可调用下层，下层不主动调用上层。

#### 原则二：按任务生命周期选择

| 任务生命周期 | 机制 | 说明 |
|------------|------|------|
| 秒级（< 1 分钟） | 直接执行 | 简单查询、记忆检索 |
| 分钟级（1~10 分钟） | `delegate_task` | 代码审查、技术分析 |
| 小时级（10 分钟~数小时） | Kanban 分派 | 调研、方案设计、文档撰写 |
| 持续运行 | Profile 多进程 | 人格 Agent、监听服务 |

#### 原则三：Profile 是「身份」，delegate_task 是「工具」

- **Profile 多进程** → 独立人格、长期在线、有记忆
- **delegate_task** → 临时调用技能、不保留状态、用完即走

```
如音作为独立 Profile：老大可以在飞书上直接找如音说话
delegate_task 召唤如音：银月在内部临时请如音帮忙分析
```

#### 原则四：Kanban 做「跨 Agent 工作流编排」

当任务需要**多个 Agent 接力完成**时，走 Kanban：

```
任务：调研 vLLM 部署方案
  1. 紫灵 → 需求分析（Kanban Task 1）
  2. 如音 → 技术实现（Kanban Task 2，依赖 Task 1）
  3. 思月 → 文档归档（Kanban Task 3，依赖 Task 2）
```

每个步骤异步执行，互不阻塞。

### 6.3 Profile + delegate_task 的配合策略

目前姐妹既是独立 Profile 又是可 delegate_task 的 skill。这种「双形态」设计很有价值：

| 维度 | 作为独立 Profile | 作为 delegate_task skill |
|------|-----------------|------------------------|
| **触发方式** | 老大直接 @ 姐妹 | 银月内部委托 |
| **对话形式** | 独立对话历史 | 子进程一次性调用 |
| **记忆维护** | 自主维护 MEMORY.md | 无记忆，用完即忘 |
| **场景** | 长期沟通、持续任务 | 短期判断、即时分析 |

**建议**：保持双形态，无需二选一。

### 6.4 通信拓扑建议

#### 当前（可用）

```
飞书群聊模式：
  老大 ──► 飞书群 ──► 银月、如音、思月、紫灵都在群里
                    ◄── 姐妹们在群里回复 → 老大看到全过程
```

#### 未来优化方向

```
智能路由模式：
  老大发消息到银月
    ├─ 技术问题 → 银月 delegate_task 如音 或 转发给如音
    ├─ 需求创意 → 银月 delegate_task 紫灵 或 转发给紫灵
    └─ 文档相关 → 银月 delegate_task 思月 或 转发给思月
  银月汇总回复老大
```

两种模式可并存，取决于老大的偏好。

## 七、潜在问题与应对

### 7.1 上下文丢失

**问题**：`delegate_task` 时，子 Agent 没有父 Agent 的对话历史，需要手动传 context。

**应对**：
- 传递足够的背景信息（问题描述、相关文件路径、历史决策）
- 关键上下文写入 MEMORY.md，子 Agent 可读取
- 使用 Kanban 的注释线程积累上下文

### 7.2 重复工作

**问题**：多个 SubAgent 可能做重复的调研或实现。

**应对**：
- Kanban 的任务依赖链避免并行冲突
- 子 Agent 启动时先 `kanban_show` 检查状态
- 定期 `session_search` 检索是否已有类似工作

### 7.3 API 消耗膨胀

**问题**：多 Agent + 多 SubAgent 导致 API 调用量翻倍。

**应对**：
- 遵循选型指南，不滥用 SubAgent
- 简单任务直接执行，不走委托
- Kanban 任务合并批处理
- 独立 Profile 各自控制模型选择（如音用强模型，思月用中模型）

### 7.4 状态不一致

**问题**：Profile 进程和 Kanban DB 状态可能不同步。

**应对**：
- 任务开始前 `kanban_show` 确认状态
- 进程重启后从 Kanban 恢复未完成任务
- 定期 `memory-inspection` 巡检记忆一致性

## 八、最佳实践总结

### 8.1 Do's

| 实践 | 说明 |
|------|------|
| ✅ 按生命周期选机制 | 秒级直接执行，分钟级 delegate_task，小时级 Kanban |
| ✅ 保留 Profile 双形态 | 既支持独立对话，又支持内部委托 |
| ✅ context 传足不传杂 | 只传子 Agent 需要的信息，不要 dump 整段对话 |
| ✅ 用 Kanban 管理依赖链 | 跨 Agent 协作时明确上下游关系 |
| ✅ 任务完成后清理 | 关闭 tmux 会话、删除临时文件 |

### 8.2 Don'ts

| 禁忌 | 后果 |
|------|------|
| ❌ 能用 delegate_task 却走 Kanban | 增加不必要的调度延迟 |
| ❌ 持续运行的任务用 delegate_task | 50 轮限制会中断任务 |
| ❌ 多个 SubAgent 改同一文件 | 冲突覆盖 |
| ❌ SubAgent 不验证就返回结果 | 父 Agent 可能收到错误结果 |
| ❌ 给 SubAgent 传递无关上下文 | 浪费 token，降低推理质量 |
