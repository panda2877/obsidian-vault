## 二、自我实现功能完整清单

### 2.1 已在源码中实现的改动

#### A. profile-aware SOUL.md 加载（prompt_builder.py）
- **文件：** `agent/prompt_builder.py`
- **逻辑：** 优先加载 `<HERMES_HOME>/SOUL.md`，若不存在则 fallback 到 `~/.hermes/SOUL.md`
- **用途：** 多 profile 模式下，各姐妹加载自己的人格设定

#### B. API Server 会话管理端点（api_server.py）
- **文件：** `gateway/platforms/api_server.py`
- **功能：** `GET /api/sessions`（列表）和 `GET /api/sessions/{key}`（详情）
- **用途：** Dashboard 可查看所有会话状态

#### C. MEDIA 路径严格验证（base.py）
- **文件：** `gateway/platforms/base.py`
- **功能：** MEDIA 标签只接受绝对路径（`/` 或 `~/` 开头）+ `os.path.isfile()` 校验
- **用途：** 防止路径穿越和无效 MEDIA 引用

#### D. 微信 aiohttp 3.13+ 兼容（weixin.py）
- **文件：** `gateway/platforms/weixin.py`
- **功能：** 所有 aiohttp 请求改用 `ClientTimeout` 传参 + try/except TimeoutError
- **原因：** aiohttp 3.13+ 对跨 event loop 的 `asyncio.timeout()` 抛异常

#### E. /resume 默认跳转 session-wechat（run.py）
- **文件：** `gateway/run.py`
- **功能：** `/resume` 无参数时，优先跳到 "session-wechat"，无则回退到最新会话
- **用途：** 微信端快速恢复

#### F. send_feishu_notification 工具（send_message_tool.py）
- **文件：** `tools/send_message_tool.py`
- **功能：** 同步包装函数，默认发到飞书群 `oc_08a798e06860c6b905f8090aec40208b`
- **用途：** 内部 bypass.log 通知等场景

#### G. Skills owner-lock（skills_tool.py — 已删除）
- **文件：** `tools/skills_tool.py`（commit 8f3893f4 添加，commit 5182ecc0 删除）
- **功能：** L4 级 skill 调用拦截，基于 skills-index.json 中的 owner 字段
- **当前状态：** ❌ 已删除（因为和 v0.13 kanban worker 任务归属机制冲突）

#### H. agent_registry 表（kanban_db.py）
- **文件：** `hermes_cli/kanban_db.py`
- **功能：** 新增 `agent_registry` 表 + CRUD 操作（register_agent/update_agent_status/get_agent/list_agents）
- **用途：** 记录各 agent 的身份、角色、能力、状态，用于 board 可见性和任务路由

#### I. Snapshot Plugin + Tasks Store（新文件）
- **文件：** `plugins/memory/snapshot/tasks_store.py` + `tests/agent/test_snapshot_provider.py`
- **功能：** SQLite 任务状态追踪（tasks/agents 表），Status: backlog|inbox|assigned|in_progress|review|done
- **特点：** 使用公共看板目录 `~/.hermes/kanban/`，所有 profile 共享

## 四、冲突与兼容性分析

### 🔴 高冲突 — 需要手动处理

#### 冲突 1：kanban_db.py — agent_registry 表 vs v0.13 Multi-Agent Kanban
- **我们的改动：** 在 `kanban_db.py` 中新增了 `agent_registry` 表 + CRUD API
- **v0.13 改动：** Multi-Agent Kanban 完全重写了看板系统，包含心跳、reclaim、僵尸检测、任务重试、幻觉门等
- **冲突点：** v0.13 有完整的多 agent 看板实现，可能已经包含了类似或更好的 agent 注册/发现机制。我们的 agent_registry 表可能与 v0.13 的 schema 冲突
- **风险：** ⚠️ 高 — merge 时 kanban_db.py 会大范围冲突

#### 冲突 2：skills_tool.py — 文件被两个自定义 commit 修改
- **8f3893f4 添加** owner-lock 拦截逻辑
- **5182ecc0 删除** 该逻辑（我们手动回退了）
- **v0.13 改动：** skills_tool.py 可能有很多上游更新
- **风险：** ⚠️ 中 — 文件已被反复修改，diff 基础复杂

#### 冲突 3：api_server.py — /api/sessions 端点
- **我们的改动：** 添加了 `_handle_list_sessions` 和 `_handle_get_session` 两个端点
- **v0.13 改动：** 可能也有类似端点（Dashboard 增强、Profiles 管理）
- **风险：** ⚠️ 中 — 路由注册可能重复

#### 冲突 4：prompt_builder.py — SOUL.md 加载逻辑
- **我们的改动：** 重写了 `load_soul_md()`，增加 profile 优先 + 全局 fallback
- **v0.13 改动：** 上游可能也有修改（特别是 multi-profile 相关的改动）
- **风险：** ⚠️ 中 — 函数逻辑被完全替换，merge 时可能冲突

### 🟡 中风险 — 需验证

#### 风险 5：gateway/run.py — /resume 逻辑
- 我们的改动替换了 /resume 无参数的整个处理逻辑
- v0.13 有"会话持久化"功能，可能也修改了 resume 逻辑
- 需验证 v0.13 的 resume 实现是否兼容我们的 session-wechat 默认跳转

#### 风险 6：send_message_tool.py — send_feishu_notification
- 我们在文件末尾添加了辅助函数
- v0.13 可能新增了类似功能（平台通知相关改动很多）
- 如果 v0.13 也新增了函数，可能导致命名冲突

#### 风险 7：weixin.py — aiohttp 兼容修复
- 我们的改动是 bug fix，v0.13 可能已经修了这个问题
- 如果是上游已修复，我们的改动会冗余但不冲突
- 需要验证 v0.13 是否已解决 aiohttp 3.13+ 兼容性

### 🟢 低风险 — 可安全合并

#### 风险 8：base.py — MEDIA 路径验证
- 我们的改动是安全加固
- v0.13 安全波包含很多安全修复，可能也有类似改动
- 冲突概率低

#### 风险 9：snapshot plugin（新文件）
- `plugins/memory/snapshot/tasks_store.py` 和 `tests/agent/test_snapshot_provider.py`
- 全新文件，不会与上游冲突
- 但功能可能与 v0.13 的 Checkpoints v2 重叠

## 六、升级策略建议

### 方案 A：保守策略 — 只 cherry-pick 安全补丁
1. 识别 v0.13 中不涉及我们改动文件的 commit（安全修复、新功能）
2. 逐个 cherry-pick 到当前分支
3. 保留我们的自定义改动
4. **优点：** 风险最小
5. **缺点：** 错过大版本功能更新，长期维护成本高

### 方案 B：激进策略 — 完全 rebase 到 v0.13
1. 在 v0.13 tag 上创建新分支
2. 逐个重新应用我们的 3 个自定义 commit（需解决冲突）
3. 对每项改动评估是否需要用 v0.13 的功能替代
4. **优点：** 获得全部新功能
5. **缺点：** 工作量大，kanban_db.py 等核心文件冲突严重

### 方案 C：推荐策略 — 分阶段升级
1. **第一阶段（安全补丁）：** cherry-pick v0.13 中不影响我们改动的安全修复和小功能
2. **第二阶段（kanban 评估）：** 对比 v0.13 的 Multi-Agent Kanban 和我们的实现，决定方向
3. **第三阶段（核心升级）：** 处理 kanban_db.py 等核心冲突文件，迁移到 v0.13 方案
4. **第四阶段（优化）：** 启用 `/goal`、post-write lint 等新功能
