## 一、现状与问题

### 1.1 现有记忆机制

| 层级 | 存储位置 | 容量 | 加载方式 | 利用率 |
|------|---------|------|---------|-------|
| 短期（会话） | LLM context window | Token 上限 | 自动 | ✅ 100% |
| 中期（日志） | `memories/` 目录 | 无限制 | 需主动读取 | ❌ 0% |
| 长期（永久） | MEMORY.md + USER.md | 2200+1375 字符 | 每次启动自动 | ⚠️ 有内容无维护 |

### 1.2 核心问题

1. **无中期层**：跨天任务无法接续，上下文全靠重新描述
2. **MEMORY.md 只增不减**：长期积累超过 2200 字符上限后会丢失早期内容
3. **无巡检机制**：失效规则不会被清理，MEMORY.md 越来越臃肿
4. **姐妹协作信息孤岛**：各姐妹独立记忆，对同一项目的认知可能不一致

## 二、三层记忆架构设计

### 2.1 层级定义

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：会话级（自动）                                      │
│  当前对话的上下文，由 LLM 原生管理                            │
│  - 会话结束后即销毁                                          │
└─────────────────────────────────────────────────────────────┘
                          ↓ 主动归档
┌─────────────────────────────────────────────────────────────┐
│  第二层：中期记忆（日志）                                     │
│  路径：~/.hermes/profiles/{name}/memories/YYYY-MM-DD.md     │
│  - 每日自动生成                                             │
│  - 包含：任务进度、关键决策、遗留问题、下一步行动              │
│  - 下次启动时读取，自动接续                                   │
└─────────────────────────────────────────────────────────────┘
                          ↓ 定期提炼
┌─────────────────────────────────────────────────────────────┐
│  第三层：长期记忆（永久）                                     │
│  路径：~/.hermes/profiles/{name}/MEMORY.md（根目录）         │
│  路径：~/.hermes/profiles/{name}/USER.md（根目录）           │
│  路径：~/.hermes/profiles/{name}/memories/MEMORY.md（备份）  │
│  - MEMORY.md（根目录）：技术规范、分工规则、工具路径        │
│  - memories/MEMORY.md：自动备份（与根目录同步）             │
│  - USER.md（根目录）：老大偏好、沟通风格、禁止事项          │
│  - 字符限额：2200 + 1375                                     │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 各姐妹的记忆分工

| 姐妹 | MEMORY.md 重点 | USER.md 重点 |
|------|---------------|-------------|
| 银月 | 项目全局状态、当前任务进度、协作路由规则 | 老大沟通偏好 |
| 如音 | 技术规范、服务器环境、已知 Bug、工具配置 | 分工边界、技术偏好 |
| 思月 | 文档归档状态、知识库结构、归档流程规范 | 老大文档偏好 |
| 紫灵 | 需求创意规范、产品设计知识、创意标准 | 老大创意偏好 |

### 2.3 文件结构总览

| 文件/目录 | 位置 | 作用 |
|-----------|------|------|
| SOUL.md | `~/.hermes/profiles/{name}/SOUL.md` | 角色定义、性格话术、协作边界 |
| MEMORY.md | `~/.hermes/profiles/{name}/MEMORY.md` | 长期记忆：技术规范、分工规则、环境信息 |
| USER.md | `~/.hermes/profiles/{name}/USER.md` | 老大偏好、沟通风格、禁止事项 |
| memories/ | `~/.hermes/profiles/{name}/memories/YYYY-MM-DD.md` | 中期记忆：每日日志 |
| skills/ | `~/.hermes/profiles/{name}/skills/{category}/{skill-name}/` | 可复用技能库 |
| CHANGELOG.md | `~/.hermes/profiles/{name}/CHANGELOG.md` | 记忆变更记录 |
| 文档归档 | `~/obsidian-vault/` | 姐妹们的工作文档（思月维护） |

## 三、中期记忆层实施

### 3.1 日志文件格式

路径：`~/.hermes/profiles/{name}/memories/YYYY-MM-DD.md`

```markdown
# {YYYY-MM-DD} 工作日志 — {姐妹名}

## 今日完成
-

## 进行中
-

## 待处理
-

## 关键决策
-

## 遗留问题
-
```

### 3.2 启动时自动读取机制

**说明**："启动"指**新建 session**（即银月发起新对话），而非重启网关。每次新建 session 时加载完 SOUL/MEMORY 后，自动进入读取流程。

**问题**：各姐妹每次启动都是空白状态，不知道昨天做了什么。

**解决**：在 SOUL.md 或 MEMORY.md 中固化启动流程，每次新建 session 后先读取近期日志。

```bash
# 在 MEMORY.md 开头固化：
## 启动流程
每次启动时：
1. 读取 memories/ 目录下近 3 天的日志文件
2. 从日志中提取「进行中」和「待处理」事项
3. 若有未完成的上文任务，主动询问老大是否接续
4. 额外读取 ~/.hermes/profiles/shared/role-responsibility.md，作为记忆的一部分
```

### 3.3 任务交接时写入日志

当姐妹之间需要交接任务时，交出方必须写入日志：

```markdown
## 任务交接：{任务名} → {接替姐妹}
- 当前进度：...
- 关键信息：...
- 注意事项：...
- 接替者需要：...
```

## 四、心跳巡检机制（长期记忆维护）

### 4.1 问题

MEMORY.md 有 2200 字符上限，长期只增不减会导致：
- 早期重要规则被挤出
- 失效规则占用空间
- 记忆质量下降

### 4.2 巡检 Cron 任务

为每个姐妹创建每日巡检 Cron：

```bash
# 如音的巡检 Cron
hermes cron create "0 21 * * *" \
  --name "如音-记忆巡检" \
  --profile xingruyin \
  --message "执行记忆巡检任务：
1. 读取 memories/ 近 3 天日志，提炼新增的重要规则
2. 检查 MEMORY.md 当前字符数：
   - 若超过 1800 字符，执行压缩（清理失效记录、精简长表述）
   - 若不超过 1800 字符，本次跳过压缩
   - 若连续 3 次无需压缩，提示老大考虑将长规范迁移为 skill
3. 将本次巡检结果写入 memories/YYYY-MM-DD.md" \
  --deliver origin
```

**压缩触发条件**：MEMORY.md 实际字符数 > 1800
**"无法精简"时的处理**：在当天日志中记录"本次无需压缩"；若连续 3 次均无需压缩，主动提示老大将部分规范迁移至独立文件或提炼为 skill。

### 4.3 巡检检查清单

```
记忆巡检清单：
□ 读取 memories/ 近 3 天日志
□ 提取新出现的规范/决策/偏好
□ 更新 MEMORY.md（新增重要内容）
□ 清理失效的临时记录
□ 若 MEMORY.md > 1800 字符，执行精简压缩
□ 评估是否有长规范可提炼为独立 skill
□ 在当天 memories 日志中记录本次巡检结果
```

### 4.4 日志记忆时间窗口

- **窗口范围**：前一天北京时间 03:00 → 当天北京时间 03:00（24小时滑动窗口）
- **时区**：Asia/Shanghai (CST, UTC+8)
- **说明**：以凌晨3点作为分界线，刚好卡在两个工作日之间，覆盖完整"工作日"内容

## 七、Agent 委托协作机制

### 7.1 背景与问题

**现状问题**：

```
老大问银月技术问题 → 银月转发给如音 → 如音回复银月 → 银月转达老大
```

链条问题：
- **信息折损**：转发容易丢失上下文
- **延迟**：多一跳响应
- **银月负担**：需要理解技术内容再转述

**平台限制**：飞书禁止 bot@bot，无法通过 @mention 判断同群；bot 无法主动加入一个没有它存在的群。

### 7.2 解决方案：delegate_task + agent-delegate skill

**核心流程**：

```
老大在任意会话问银月技术问题
    ↓
银月使用 delegate_task 召唤如音，附加 agent-delegate skill
    ↓
如音自动加载自己的 SOUL + MEMORY + USER
    ↓
如音直接回答 → 返回银月 → 银月直接转发（声明来源）
```

### 7.3 agent-delegate skill

**路径**：`~/.hermes/profiles/xingruyin/skills/autonomous-ai-agents/agent-delegate/SKILL.md`

**各姐妹身份定义**：

| 姐妹 | 定位 | 话术风格 |
|------|------|---------|
| 银月 | main-agent：任务分派、协作路由、老大沟通桥梁 | 亲密灵动，语气可爱 |
| 如音 | 技术专家：技术问题解决 & 工程实现专家 | 先说结论，再给分析；只叫「老大」 |
| 思月 | 文档专家：文字输出 & 文档资产管理专家 | 结论先行，一针见血；只叫「老大」 |
| 紫灵 | 需求专家：需求挖掘 & 方案设计专家 | 傲娇语气，喜欢唱反调 |

### 7.4 调用方式

```python
delegate_task(
    goal="你是如音，处理XXX技术问题",
    skills=["agent-delegate"]
)
```

**⚠️ 注意**：必须使用 goal 单任务模式，不要使用 tasks 批量模式。tasks 模式不传递 skills 参数。

### 7.5 路径精确性说明

**⚠️ 注意全局 memories 目录**：`~/.hermes/memories/` 是全局共享目录，**不是**各姐妹的个人目录。各姐妹的文件在 `~/.hermes/profiles/{name}/` 下。

| 文件 | 路径 |
|------|------|
| SOUL.md | `~/.hermes/profiles/{name}/SOUL.md` |
| MEMORY.md | `~/.hermes/profiles/{name}/MEMORY.md` |
| USER.md | `~/.hermes/profiles/{name}/USER.md` |

### 7.6 跨会话处理

- **同一会话内**：银月 delegate_task 召唤如音 → 如音在当前会话回答 → 银月转发
- **跨会话**：delegate_task 召唤如音 → 如音回复 → 银月将结论发回原会话并声明来源
- 思月在日志中记录该次协作（形成跨会话追踪）

### 7.7 委托触发规则

**何时该委托**：
- 任务超出当前 Agent 职责范围
- 老大明确要求某位姐妹处理
- 需要其他 Agent 的专业知识（技术/文档/需求）

**何时不该委托**：
- 任务在自身职责范围内
- 简单查记忆就能回答的问题（直接查自己的 MEMORY.md）
- 纯转发类问题（不是技术/文档/需求问题）

**职责边界（各 Agent 引用共享配置）**：

| 姐妹 | 职责范围 |
|------|---------|
| 银月 | 全局协调、任务分派、老大沟通 |
| 如音 | 技术实现、Bug排查、技术方案 |
| 思月 | 文档归档、知识管理、审计追踪 |
| 紫灵 | 需求分析、创意设计、产品规划 |

### 7.8 公共配置管理

**架构原则**：
- 各 Agent 私有记忆：写在自己目录，只读自己的 → 无冲突
- 公共配置（角色职责表等）：大家只读，银月唯一写入 → 无冲突

**公共配置路径**：`~/.hermes/profiles/shared/role-responsibility.md`

## 八、落地步骤

### 8.1 记忆管理

| 项目 | 说明 |
|------|------|
| 管理原则 | 各 Agent 自己管自己的记忆（MEMORY.md） |
| 审核机制 | 银月定期复核姐妹们的记忆 |
| 变更触发 | 任务结束后、角色被召唤时、大版本更新后 |

### 8.2 Cronjob 设置

**全局记忆同步 Cronjob**（统一维护）：
- 用途：定期让各 Agent 审视自己的记忆，清理过期内容、补充新内容，并将审视结果汇总
- 触发时间：**每天北京时间 03:00**（非工作时段，服务器负载低）
- 数量：1 个全局 cronjob（银月维护）

**各 Agent 独立巡检 Cronjob**（分散维护）：
- 用途：各 Agent 独立执行记忆巡检（第四章心跳巡检机制）
- 触发时间：每天 21:00
- 数量：4 个分散 cronjob（如、音、思月、紫灵各一条）

### 8.3 委托流程规范

1. **触发条件判断**：根据职责边界判断是否需要委托
2. **goal prompt 构造**：明确指定 profile 路径，禁止 search_files，直接 read_file 精确路径
3. **结果回传**：银月直接转发，不加润色，声明来源

## 十、Skill 管理机制

> 版本：v2.1（2026-04-29 讨论定稿）

### 11.1 背景与目标

多Agent协作体系中，skill 作为核心能力单元，存在以下问题：
- skill 数量增长后难以快速定位
- 调用时未强制匹配最佳 skill
- 跨 Agent 分工边界模糊，容易绕过分工原则
- trigger_scenes / keywords 等元数据缺失或不完整

本方案旨在建立一套完整的 skill 管理机制，包括索引体系、调用规范、分工防护和持续优化。

### 11.2 索引表设计

#### 11.2.1 存储位置

```
~/.hermes/skills-index/
  ├── skills-index.json    # 底层索引（机器可读）
  └── skills-index.md      # 可读视图（人可读）
```

#### 11.2.2 索引结构（skills-index.json）

```json
{
  "version": "2026-04-29",
  "skills": [
    {
      "name": "agent-delegate",
      "path": "autonomous-ai-agents/agent-delegate",
      "owner": "shared",
      "category": "autonomous-ai-agents",
      "purpose": "多Agent委托协作标准skill，银月用delegate_task召唤如音/紫灵/思月时使用",
      "trigger_scenes": ["召唤sub-agent", "任务分发", "多Agent协作"],
      "keywords": ["delegate", "spawn", "sub-agent", "召唤", "任务分发"],
      "dependencies": [],
      "last_updated": "2026-04-29"
    }
  ]
}
```

#### 11.2.3 字段说明

| 字段 | 说明 |
|------|------|
| `name` | skill名称，唯一标识 |
| `path` | 相对于 skills 目录的路径 |
| `owner` | 归属：`xingruyin`（如音专属）、`ziling`（紫灵专属）、`wensiyue`（思月专属）、`shared`（共享） |
| `category` | 职能分类，复用现有 category 体系 |
| `purpose` | 一句话用途描述 |
| `trigger_scenes` | 触发场景列表（中文，便于匹配中文任务描述） |
| `keywords` | 关键词（中英文，用于语义匹配） |
| `dependencies` | 依赖的其他 skills |
| `last_updated` | 最后更新时间 |

#### 11.2.4 索引调用机制（强制）

```
任务描述输入
    │
    ▼
skill-index skill 自动加载
    │
    ▼
读取 skills-index.json
    │
    ▼
三层匹配
  ├── L1：category 精确匹配
  ├── L2：trigger_scenes / keywords 关键词匹配
  └── L3：purpose + description 语义模糊匹配
    │
    ▼
返回推荐 skill（top 1-3），含 owner、匹配理由
    │
    ▼
owner = shared → 自行加载执行
owner = 如音/紫灵/思月 → delegate_task 委托执行
```

### 11.3 分工防护机制

#### 11.3.1 硬拦截

银月调用任何 skill 前，必须经过 skill-index 匹配。

```
银月尝试直接调用 [非shared skill]
    │
    ▼
skill-index 校验 owner
    │
    ├── owner = shared → 允许调用
    │
    └── owner = 如音/紫灵/思月 → 直接拒绝
        │
        ▼

```

#### 11.3.2 豁免机制

当目标 sub-agent 不在线或不可用时，允许临时豁免：

```
银月尝试调用 [skill-name]
    │
    ▼
硬拦截触发
    │
    ├── sub-agent 在线 → 推送审批请求给 sub-agent
    │     │
    │     ▼
    │   sub-agent 收到飞书审批
    │   「银月申请调用 [skill-name]
    │    原因：[银月填写]
    │    [批准] [拒绝] [5分钟后自动批准]」
    │     │
    │     ▼
    │   批准 → 记录豁免 → 允许调用
    │   拒绝 → 拒绝调用
    │   超时 → 自动批准（计入统计）
    │
    └── sub-agent 离线/忙碌
          │
          ▼
        自动批准临时豁免（单次有效）
```

| 场景 | 有效期 | 说明 |
|------|--------|------|
| sub-agent 在线，审批通过 | 单次调用 | 记录在案，统计中 |
| sub-agent 离线/忙碌 | 单次调用 | 注明原因，不扣分 |

- **每周巡检**：hermes-memory-maintenance cronjob 生成周报，包含拦截次数、趋势分析

### 11.4 sub-agent 信任积分机制

#### 11.4.1 积分规则（仅针对 sub-agent）

| 操作 | 积分变化 |
|------|----------|
| 初始分 | 100 分 |
| 正常完成任务 | +0（维持） |
| 主动发现并修复 bug | +1 |
| 主动优化（性能/流程） | +1 |
| 任务超时/失败 | -2 |
| 主动绕过分工 | -10 |

下限：0 分（不会变负）

#### 11.4.2 积分与权限联动

| 积分区间 | 权限状态 |
|----------|----------|
| ≥80 分 | 正常权限 |
| 60-79 分 | 高风险操作需审批（删除文件、跨分工操作、批量操作限流） |
| <60 分 | 所有关键操作需审批，调用频率限制（5次/分钟 → 2次/分钟） |

#### 11.4.3 审批请求

如积分不足，sub-agent 可向老大发送审批请求：
```
「如音积分58分，执行敏感操作需审批
 操作：删除 /tmp/test.log
 [发送审批请求]」
```

老大回复后执行。

#### L1 实施框架：初始化 skills-index.json


步骤：
1. 扫描 ~/.hermes/skills/ 下所有 SKILL.md 文件
2. 提取文件名作为 skill name，目录结构作为 category
3. 读取 SKILL.md 头部 YAML/JSON 提取 trigger_scenes、keywords、purpose
4. 生成 skills-index.json 初稿（owner 暂填 shared）
5. 银月手工补充 owner 归属
```

**扫描命令示例**：
```bash
find ~/.hermes/skills/ -name "SKILL.md" -exec dirname {} \; | while read dir; do
  skill_name=$(basename "$dir")
  category=$(basename "$(dirname "$dir")")
  echo "{\"name\":\"$skill_name\",\"path\":\"$category/$skill_name\",\"owner\":\"shared\",\"category\":\"$category\"}"
done > ~/.hermes/skills-index/skills-index.json
```

#### L3 实施框架：MEMORY.md 索引摘要初始化


目标：打破 skill-index skill 与 skills-index.json 的循环依赖

实现方式：
- 初始化时扫描 ~/.hermes/skills/ 目录，读取各 SKILL.md 头部元数据
- 将 skills-index.json 关键字段（name/path/category/owner）同步到各姐妹 MEMORY.md 索引区
- 运行时直接查询 MEMORY.md 中的索引摘要，无需额外 skill
- skills-index.json 仅用于人工查阅和审计，不作为运行时依赖

索引摘要格式（写入各姐妹 MEMORY.md）：
```markdown
## Skills 索引摘要
| name | category | owner | 用途 |
|------|----------|-------|------|
| agent-delegate | autonomous-ai-agents | shared | 多Agent委托协作 |
| systematic-debugging | software-development | xingruyin | 系统性Bug排查 |
| obsidian | note-taking | wensiyue | Obsidian笔记管理 |
...
```

Token 消耗分析：
- 50 个 skills，索引约 3KB ≈ 750 tokens
- 启动时读一次，后续直接查，不重复消耗
