## 一、问题定义

### 1.1 痛点

| 场景 | 问题 |
|------|------|
| **Session 结束无法快速恢复上下文** | 会话结束后，进程退出，上下文全部丢失。下次新会话启动时没有任何残留记忆，只能靠 session_search 手动检索 |
| **任务转交时无法连带记忆** | delegate_task 转交给 subagent 时，subagent 有独立进程和 memory provider，但没有任何来自父 agent 的上下文 |

### 1.2 现有系统分析

**现有 memory provider（语义记忆）：**

- mem0 / Zep / Honcho 等：存储经 LLM 提取后的 facts/entities
- MemOS（memos 插件）：独立记忆 OS，有 Hermes 集成，存的是提取后的事实，不是原始会话快照
- **共同缺陷**：都是语义压缩后的信息，不是原始会话快照，有信息损失

**Hermes 内置记忆：**

- MEMORY.md / USER.md：2200/1375 字符限制，冻结快照机制，按需加载
- `session_search`：可搜索历史，但不会自动注入上下文，需模型主动调用

**结论：** 现有系统无法满足"原始会话快照"需求，需要新增机制。

---

## 二、核心设计原则

1. **任务驱动**：快照内容以"任务相关信息"为核心，而非完整对话日志
2. **原始快照优先**：保存原始会话上下文，不做语义压缩，确保信息不丢失
3. **所有 agent 共享 provider**：每个独立 agent（独立网关 + workspace）都运行自己的 memory provider 实例
4. **文件持久化**：快照写入文件系统，不依赖内存

## 三、方案一：MemoryProvider 插件（完整实现）

### 3.1 架构可行性 ✓

**源码确认事实：**

- `plugins/memory/__init__.py` 的 `load_memory_provider(name)` 支持从 `plugins/memory/<name>/`（打包）和 `$HERMES_HOME/plugins/<name>/`（用户）加载
- `run_agent.py`（L1442-1486）读取 `memory.provider` 配置项，激活对应 provider
- **内置 BuiltinMemoryProvider 永远存在**，外部 provider与其共存，不冲突

**Plugin 目录结构：**

```
$HERMES_HOME/plugins/memory/snapshot/
├── __init__.py          # SnapshotMemoryProvider 类
└── plugin.yaml          # name, version, hooks
```

**plugin.yaml 示例：**

```yaml
name: snapshot
version: 1.0.0
description: "会话快照 provider — 写入/读取原始会话上下文"
hooks:
  - on_session_end
pip_dependencies: []
```

### 3.2 `on_session_end` 钩子（写入快照）✓

**接口确认：**

```python
# memory_provider.py L153
def on_session_end(self, messages: List[Dict[str, Any]]) -> None:
    """Called when a session ends (CLI exit, /reset, gateway expiry).
    NOT called per-turn — only at actual session boundaries."""
```

**触发时机（已确认）：**
- CLI exit（`/exit`、`Ctrl+C`）
- `/reset`
- Gateway session 驱逐
- 上下文压缩导致 session_id 轮换（`commit_memory_session`）
- AIAgent 析构（`shutdown_memory_provider`）

**messages 参数结构：** 完整会话历史，`[{role, content, ...}, ...]`，原材料齐全。

**快照内容策略：**

以任务相关信息为核心，具体提取：

| 字段 | 内容 |
|------|------|
| `session_id` | 当前 session 标识 |
| `timestamp` | 结束时间戳 |
| `task_goals` | 任务目标列表 |
| `checklist` | 里程碑清单（只记里程碑 + 完成情况） |
| `assignments` | 节点负责人 |
| `missing_info` | 缺失信息（可空，主动提醒补齐） |
| `messages` | 原始消息（tool_calls 结果截断，保留结构） |

**写入逻辑：**

```python
def on_session_end(self, messages: List[Dict[str, Any]]) -> None:
    snapshot_data = {
        "session_id": self._session_id,
        "timestamp": time.time(),
        **self._extract_task_context(messages),  # 提取任务相关信息
        "messages": self._truncate_messages(messages),  # 截断后保留结构
    }
    snapshot_path = self._get_snapshot_path()
    with open(snapshot_path, "w") as f:
        json.dump(snapshot_data, f, ensure_ascii=False)
```

**`_extract_task_context` 算法设计要点：**
- 任务目标：扫描 user message，识别任务声明语句（如"帮我开发XXX"、"完成YYY任务"）
- check list：扫描包含 `[ ]` 或 `TODO` 标记的语句，提取里程碑 + 完成状态
- 节点负责人：扫描 `@某人` 或"由谁负责"等模式
- 缺失信息：当提取的任务目标不足以生成可执行任务时，`missing_info` 字段标记缺失项并提醒用户补齐
- 委托链：由 `on_delegation` 钩子自动追加，记录 `task + result + child_session_id`

### 3.3 快照读取机制（新 session 恢复）

**架构盲点：** `on_session_end` 只负责写入，没有配套的"session 启动时自动读取"原生钩子。

**解法：** 在 `system_prompt_block()` 里扫描 `~/.hermes/profiles/<profile>/memory/snapshot/` 目录，基于时间戳取最新的快照文件。

```python
def system_prompt_block(self) -> str:
    snapshot = self._load_latest_snapshot()
    if snapshot:
        return (
            f"<previous-session-snapshot>\n"
            f"[Session: {snapshot['session_id']} | "
            f"Time: {datetime.fromtimestamp(snapshot['timestamp']).isoformat()}]\n\n"
            f"## 任务目标\n"
            f"{self._format_task_goals(snapshot.get('task_goals', []))}\n\n"
            f"## 里程碑\n"
            f"{self._format_checklist(snapshot.get('checklist', []))}\n\n"
            f"## 缺失信息\n"
            f"{snapshot.get('missing_info', '无')}\n"
            f"</previous-session-snapshot>"
        )
    return ""

def _load_latest_snapshot(self) -> Optional[dict]:
    snapshot_dir = self.hermes_home / "memory" / "snapshot"
    snapshot_files = list(snapshot_dir.glob("*.json"))
    if not snapshot_files:
        return None
    latest = max(snapshot_files, key=lambda p: p.stat().st_mtime)
    with open(latest) as f:
        return json.load(f)
```

**文件名约定：** 不带 session_id，基于时间戳取最新。TTL 过期策略由外部 cronjob 统一清理。

**快照过期清理：** 沿用现有 cronjob 机制，清理超过 TTL 的快照文件（如超过 7 天的快照），需要单独编写清理 cronjob。

### 3.4 任务转交（delegate_task）

**快照传递方式：**

在 context 参数里传文件路径字符串，子 agent 用 `read_file` 工具自己读取。

```python
# 父 agent 侧
snapshot_path = str(self._get_snapshot_path())
delegate_task(
    goal="继续完成XXX任务",
    context=f"快照文件位置：{snapshot_path}\n请先读取快照了解上下文"
)
```

**为什么这样可行：**
- `context` 参数是字符串，直接拼进子 agent 的系统提示词
- 子 agent 启动时 toolset 包含 `file`（`read_file` 可用），自己读文件即可
- 不需要改 delegate_tool，不需要改 provider 接口

**子 agent 读取快照后：**

模型自己解析 JSON 内容，理解任务目标、里程碑、缺失信息，然后继续执行。

### 3.5 `on_delegation` 钩子（委托结果记录）

```python
def on_delegation(self, task: str, result: str,
                  child_session_id: str = "", **kwargs) -> None:
    """父 agent 侧调用 — 记录委托任务和结果到快照"""
    self._append_delegation_record(task, result, child_session_id)
```

用于父 agent 记录"我曾经委托过这个任务，结果是什么"，追加到当前快照的 `delegation_chain` 字段。

## 四、方案二：轻量实现（skill + 快照文件）

如果插件方案成本过高，可以考虑轻量路径：

**核心思路：** 不做 MemoryProvider 插件，写一个工具函数 + 一个启动 skill

| 能力 | 实现方式 |
|------|----------|
| 快照写入 | 在 `~/.hermes/profiles/<name>/skills/` 里写一个 skill，模型在 session 结束时自动调用写入 |
| 快照恢复 | 新 session 启动时，skill 自动读取上一个快照并注入上下文 |
| 任务转交 | 委托前调用 skill 把快照写入文件，子 agent 启动参数传入文件路径 |

**优点：** 不需要理解 plugin 架构，任何人都能维护
**缺点：** 需要模型主动配合调用 skill，无法利用 `on_session_end` 原生钩子

## 六、独立 Workspace 多 Agent 场景下的额外设计规则

> 以下规则在独立 workspace 多 agent 架构下**必须遵守**，确保快照文件可跨 agent 访问和传递。

### 6.1 快照文件路径隔离（最关键）

每个 agent 独立进程、独立初始化 provider，快照路径必须基于**确定性标识**生成，不能用随机 token。

```python
def _get_snapshot_path(self) -> Path:
    # ✓ 正确：基于 timestamp 排序，读取时取最新
    # 快照命名：{agent_identity}_{timestamp}.json
    return (
        self.hermes_home
        / "memory"
        / "snapshot"
        / f"{self.agent_identity}_{int(self._session_start_time * 1000)}.json"
    )

def _load_latest_snapshot(self) -> Optional[dict]:
    # 读取时按时间戳取最新
    snapshot_dir = self.hermes_home / "memory" / "snapshot"
    snapshots = [p for p in snapshot_dir.glob(f"{self.agent_identity}_*.json")]
    if not snapshots:
        return None
    latest = max(snapshots, key=lambda p: p.stat().st_mtime)
    return json.loads(latest.read_text())
```

**路径命名原则：**
- `agent_identity`：profile 名称，区分不同 agent 实例
- `timestamp`：session 开始时间（毫秒级），保证唯一性
- 读取时按文件 mtime 取最新，不需要在委托链中传递路径

### 6.2 `initialize()` 必须接收 workspace 相关 kwargs

```python
def initialize(self, session_id: str, **kwargs) -> None:
    super().initialize(session_id, **kwargs)

    self.agent_identity = kwargs.get("agent_identity", "default")
    self._session_start_time = time.time()  # 用于快照命名
```

**注意：** 我们不需要在委托时显式传递 workspace 上下文。子 agent 启动时自己扫描 `memory/snapshot/` 目录，按时间戳取最新即可找到父快照。

### 6.3 任务转交时，子 agent 如何找到父快照

```python
# 子 agent 侧（启动时自动执行）
def system_prompt_block(self) -> str:
    # 扫描当前 identity 的所有快照，取最新
    latest = self._load_latest_snapshot()
    if latest:
        return self._format_snapshot_block(latest)
    return ""
```

**关键原则：子 agent 启动时自动读取自己 identity 下的最新快照，不需要父 agent 显式传递路径。**

### 6.4 委托记录文件要原子操作

两个 agent 可能并发写同一个委托记录文件：

```python
def on_delegation(self, task: str, result: str, **kwargs) -> None:
    record_path = self._get_delegation_record_path()

    # ✓ 原子追加：用 tempfile + rename
    tmp = record_path.with_suffix(".tmp")
    existing = json.load(record_path) if record_path.exists() else {"records": []}
    existing["records"].append({
        "task": task,
        "result": result,
        "timestamp": time.time(),
        **kwargs
    })
    json.dump(existing, tmp)
    tmp.rename(record_path)
```

### 6.5 子 agent（`skip_memory=True`）也能读快照

子 agent 初始化时 `skip_memory=True`，没有自己的 provider 实例。但它通过 `ephemeral_system_prompt`（context 参数）拿到父的快照内容，**子 agent 用 `read_file` 工具直接读取**。

因此快照内容格式必须**结构化且人类可读**，方便子 agent 解析：

```json
{
  "session_id": "20260502_080634",
  "timestamp": 1746163590,
  "workspace": "backend-api",
  "task_context": "正在开发用户认证模块，完成了 JWT 签名算法，下一步需要实现 RefreshToken 轮转",
  "delegation_chain": [
    {"task": "实现 JWT 签名", "result": "完成", "agent": "agent-1"}
  ]
}
```

### 6.6 写 Provider 时的 Checklist

| 检查项 | 要求 |
|--------|------|
| 快照路径命名 | 只能用 `agent_identity + workspace_name`，不能用随机 token |
| `initialize()` | 必须从 kwargs 提取并保存 `agent_identity`、`workspace_name`、`parent_session_id` |
| 任务转交 | 快照路径规则要让子 agent 可推导（确定性命名） |
| 文件写入 | 委托记录等并发写入场景用原子操作（tempfile + rename） |
| 快照格式 | JSON 结构化，task_context 字段要人类可读，方便子 agent 解析 |
| workspace 切换 | 新 workspace 启动时，读取的是上一个 session 的快照，不是当前 workspace 的 |

## 八、技术风险（独立 Workspace 场景）

| 风险 | 等级 | 应对 |
|------|------|------|
| `messages` 字段结构在大版本升级可能变化 | 低 | 快照存完整原始 JSON，不过度依赖字段名 |
| 子 agent `skip_memory=True` 意味着子 agent 无 provider | 中 | 子 agent 通过 `system_prompt_block()` 自动读取自己 identity 下的最新快照 |
| 快照文件增大导致 `system_prompt_block()` 超长 | 低 | 实施内容截断/摘要策略，控制在 4000 tokens 以内 |
| 多个独立 agent 场景下快照路径冲突 | 低 | 使用 `agent_identity + timestamp` 双层隔离（确定性命名，禁止随机 token） |
| 子 agent 无法反推父 agent 快照路径 | 低 | 快照路径命名 `agent_identity_timestamp`，子 agent 启动时按 mtime 取自己 identity 下最新即可 |
