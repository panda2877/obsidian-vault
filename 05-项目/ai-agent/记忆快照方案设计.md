## 一、问题定义

### 1.1 痛点

| 场景 | 问题 |
|------|------|
| **Session 结束无法快速恢复上下文** | 会话结束后，进程退出，上下文全部丢失。下次新会话启动时没有任何残留记忆，只能靠 session_search 手动检索 |
| **短平快 session 污染长任务快照** | 新 session 只做 trivial 杂务，写出的 snapshot 会盖掉真正有价值的任务快照 |
| **快照加载策略不合理** | 永远取时间最近的，不区分任务是否完成，导致真正需要回顾的长任务快照被 trivial session 冲掉 |
| **SIGKILL / 崩溃导致快照丢失** | 纯 hook 方案的盲区 — 进程被 OS 直接杀死时，`on_session_end` 根本来不及被调用 |

### 1.2 现有系统分析

**现有 memory provider（语义记忆）：**

- mem0 / Zep / Honcho 等：存储经 LLM 提取后的 facts/entities
- MemOS（memos 插件）：独立记忆 OS，有 Hermes 集成，存的是提取后的事实，不是原始会话快照
- **共同缺陷**：都是语义压缩后的信息，不是原始会话快照，有信息损失

**Hermes 内置记忆：**

- MEMORY.md / USER.md：2200/1375 字符限制，冻结快照机制，按需加载
- `session_search`：可搜索历史，但不会自动注入上下文，需模型主动调用

**结论：** 现有系统无法满足"原始会话快照 + 任务驱动"需求，需要增强 snapshot provider。

## 二、核心设计原则

1. **任务驱动**：快照内容以"任务相关信息"为核心，而非完整对话日志
2. **原始快照优先**：保存原始会话上下文，不做语义压缩，确保信息不丢失
3. **未完成优先**：新 session 加载时优先回溯"未完成"的任务快照，而非时间最近
4. **文件持久化**：快照写入文件系统，不依赖内存
5. **去 delegation**：不考虑 delegate_task 场景，简化设计
6. **进程级安全**：通过 atexit 机制覆盖 SIGTERM/SIGINT 退出场景

## 三、快照格式（v2）

### 3.1 JSON 结构

```json
{
  "schema_version": 2,
  "session_id": "oc_xxx",
  "timestamp": 1746163590.123,
  "_session_start_ms": 1746163590123,
  "task_id": "实现支付模块_a1b2c3d4",
  "finished": false,
  "task_goals": ["实现支付模块"],
  "checklist": [
    {"content": "调通支付 API", "done": true},
    {"content": "对账逻辑", "done": false}
  ],
  "assignments": ["如音", "银月"],
  "missing_info": ["支付渠道 API 文档链接"],
  "messages": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ]
}
```

### 3.2 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `schema_version` | int | 格式版本，当前 2 |
| `session_id` | string | 当前 session 标识 |
| `timestamp` | float | 快照写入时间（Unix 时间戳） |
| `_session_start_ms` | int | session 开始时间（毫秒，用于文件命名） |
| `task_id` | string | 任务唯一标识，无任务时为 `"trivial"` |
| `finished` | bool | 推断值：所有 checklist item 均为 done=true 时为 true |
| `task_goals` | list[str] | 从对话中提取的任务目标列表 |
| `checklist` | list[dict] | 里程碑列表，每项含 `content` 和 `done` |
| `assignments` | list[str] | 节点负责人列表（从 `@xxx` 模式提取） |
| `missing_info` | list[str] | 缺失信息（提醒用户补齐） |
| `messages` | list[dict] | 原始消息（tool result 截断，保留结构） |

### 3.3 task_id 生成策略

从首个 `task_goals` 内容生成，格式：`{truncated_goal}_{md5_prefix}`。

- 取 `task_goals[0]` 的小写 strip 结果
- 截取前 50 字符
- 拼接 8 位 MD5 哈希前缀
- 无 task_goals 时为 `"trivial"`

```
"实现用户认证模块" + md5("实现用户认证模块")[:8] → "实现用户认_auth3f1d2b8"
```

> **注意**：`task_id` 主要用于日志和调试，不用于快照查找。快照查找依赖 `finished` 字段。

## 四、加载策略（v2）

### 4.1 策略规则

```
system_prompt_block():
  1. load_latest_unfinished()  — 扫描所有快照，过滤 finished=false，取 mtime 最晚的
  2. load_latest()              — 降级：取 mtime 最晚的（兼容旧 snapshot 或全部已完成的场景）
  3. 以上均无 → 返回空字符串
```

### 4.2 意图

- Session A 启动长任务，做了一半后结束 → 写 snapshot（finished=false）
- Session B 只说 "hello" → 写 snapshot（finished=false，但 task_goals 为空，task_id=trivial）
- Session C 再接入 → 加载时跳过 trivial，找到 Session A 的未完成快照

### 4.3 兼容性

- 旧 snapshot（schema_version=1，无 `finished` 字段）→ `finished` 默认为 false，走 unfinished 逻辑，正常加载
- 旧 snapshot 无 `task_id` → 视为 trivial

## 五、实现详情

### 5.1 文件结构

```
plugins/memory/snapshot/
├── __init__.py
├── provider.py              # SnapshotMemoryProvider 类
├── context_extractor.py    # extract_task_context 算法
├── snapshot_store.py       # 快照读写、TTL 清理、load_latest_unfinished()
├── plugin.yaml
└── DESIGN.md               # 代码级设计文档（与本文档互补）
```

### 5.2 核心模块

**context_extractor.py**

`extract_task_context(messages)` → 返回 dict，包含：
- `task_goals`、`checklist`、`assignments`、`missing_info`、`finished`
- `finished` 推断逻辑：所有 checklist item 均为 done=true 时为 true

**snapshot_store.py**

- `write()` — 原子写入（tempfile + rename）
- `load_latest()` — 按 mtime 取最新
- `load_latest_unfinished()` — 过滤 finished=false 后按 mtime 取最新
- `expire()` — 删除 ttl_days 外的快照
- `list_snapshots()` — 返回元数据列表（调试用）

**provider.py**

- `on_session_end()` — 生成 task_id，写入 schema_version=2 的快照；并缓冲消息供 atexit 使用
- `_flush_pending(at_exit=False|True)` — 执行写入，`at_exit=True` 时跳过已正常结束的 session
- `_generate_task_id()` — 从 task_goals 生成 task_id，无目标时返回 `"trivial"`
- `system_prompt_block()` — 按加载策略优先取 unfinished 快照
- `_format_snapshot_block()` — 格式化为 `<previous-session-snapshot>` XML 块

### 5.3 写入时机

绑定 `on_session_end` hook，在 session 边界触发（CLI exit、`/reset`、超时）。

> **未来方向**：任务开始时触发写入（而非 session 结束时），避免 trivial session 污染。当前为过渡方案。

### 5.4 过期清理

由 `SnapshotStore.expire()` 在每次 `initialize()` 时执行，删除 `ttl_days` 外的快照文件。

## 六、快照保障机制（v2 新增）

### 6.1 问题背景

`on_session_end` 依赖调用方在会话边界正确触发。但如果进程收到 **SIGKILL**、**OOM** 或发生**崩溃**，`on_session_end` 根本来不及被调用 —— 这是纯 hook 方案的盲区。

### 6.2 解决方案：atexit 进程级兜底

参考 `OpenVikingMemoryProvider` 的实现，在 provider 初始化时注册 `atexit.register(_atexit_flush)`。

但与 openviking 不同，snapshot 的 `on_session_end` 需要调用方传入 `messages`——崩溃时调用栈已经消失，消息已不可访问。因此额外引入了**消息缓冲**设计。

### 6.3 机制详解

```
会话进行中:
    on_session_end(messages) 被调用
        → _pending_messages.extend(messages)     # 缓冲
        → _flush_pending(at_exit=False)         # 立即写入
        → _session_end_called = True

进程正常退出（SIGTERM / SIGINT / sys.exit）:
    atexit 触发 _atexit_flush()
        → _flush_pending(at_exit=True)          # 使用缓冲数据写入
        → 如果 _session_end_called 为 True 则跳过（避免重复）

SIGKILL / OOM / 崩溃:
    atexit 不触发（操作系统直接终止进程）          ← 仍是盲区
```

### 6.4 关键字段

| 字段 | 用途 |
|------|------|
| `_pending_messages: list[dict]` | 跨调用累积消息，atexit 依赖此缓冲 |
| `_session_end_called: bool` | 防止正常退出后 atexit 重复写入 |
| `_last_active_provider` (模块级) | atexit 回调能访问到当前 session 的 provider 实例 |

### 6.5 覆盖范围

| 场景 | 是否写入快照 |
|------|-------------|
| CLI 正常退出 | ✅ `on_session_end` 直接触发 |
| `/reset` 命令 | ✅ `on_session_end` 直接触发 |
| 会话超时 | ✅ `on_session_end` 由调用方触发 |
| SIGTERM / SIGINT | ✅ `atexit` 兜底，使用缓冲消息 |
| SIGKILL | ❌ atexit 不触发（OS 限制） |
| OOM 崩溃 | ❌ atexit 不触发（OS 限制） |
| 进程崩溃（未捕获异常） | ⚠️ 大多数崩溃会触发 Python 异常栈 unwind，atexit 可调用（SIGKILL/OOM 除外） |

### 6.6 日志标识

日志中 `source=on_session_end` 或 `source=atexit` 字段可区分写入来源。

## 七、配置项

| 字段 | 默认值 | 说明 |
|------|--------|------|
| `ttl_days` | `7` | 快照保留天数，到期自动删除 |
| `snapshot_dir` | `$HERMES_HOME/memory/snapshot` | 快照存储目录 |
| `max_tokens` | `4000` | 快照块在 system prompt 中的最大 token 数（软限制） |

激活方式：在 `config.yaml` 中设置 `memory.provider: snapshot`。

## 八、与 OpenViking 的对比

| 维度 | Snapshot | OpenViking |
|------|----------|------------|
| 存储介质 | 本地文件系统（JSON） | Volcengine OpenViking 数据库 |
| 语义提取 | 无（原始消息 + 正则解析） | 有（6 类记忆自动提取） |
| atexit 机制 | `_atexit_flush` + 消息缓冲 | `_atexit_commit_sessions`（直接调 `on_session_end([])`，无需消息） |
| 依赖 | 无外部依赖 | 需 OpenViking 服务运行 |
| 适用场景 | 轻量、无网络、离线环境 | 团队共享知识库、语义检索 |

## 九、技术风险

| 风险 | 等级 | 应对 |
|------|------|------|
| `finished` 推断不准确（用户没标记 checklist 但任务实际已完成） | 中 | 依赖用户显式维护 checklist；未来可引入显式"任务完成"信号 |
| trivial session 无 task_goals 但 finished=false，仍被优于旧任务快照加载 | 低 | `load_latest_unfinished` 按 mtime 取最新，trivial session 时间更新所以先被加载；但其 task_id=trivial，下游可识别并忽略 |
| 旧 snapshot 无 `finished` 字段 | 低 | 默认为 false，兼容 |
| 快照文件增大导致 `system_prompt_block()` 超长 | 低 | 控制在 4000 tokens 以内，内容截断 |
| SIGKILL / OOM 导致快照丢失 | 低 | atexit 无法覆盖，是 OS 限制；如需更强保障需 systemd restart 机制 |
