## 笔记

### 2026-05-09 前期调研结论：子代理调用链能力评估

> 来源：银月调研整理 — 基于 Hermes v0.13 `delegate_task` 机制的四项需求逐条分析

#### 需求①：自动分解和编排任务 ⚡半自动

- `delegate_task` 提供并行/串行子任务基础能力（`tasks` 数组），但「自动分解」无内置引擎
- 当前靠父 Agent LLM 推理拆解任务，编排逻辑需手写 skill 或代码
- 可写 `task-orchestrator` skill 让父 Agent 按固定策略分解

#### 需求②：根据任务内容选 profile + memory 分片 + skill 🛠手动可做

- `delegate_task` 子 Agent 是**轻量级克隆** — 共享父进程配置，不加载独立 profile，不自动选 skill
- 父 Agent 通过 `context` 传递 soul 定义，通过 toolsets 限制工具
- ❌ **不存在**任务内容 → soul/memory/skill 的自动映射引擎
- ❌ 子 Agent 无独立 memory，不自动加载 skill（需 context 传递角色定义后手动 `skill_view`）
- Profile 多进程模式有独立记忆和 skill，但非「用完即走」的临时子代理

#### 需求③：子代理操作过程对用户可见 ❌最大Gap

- `delegate_task` 设计哲学：**「只看结果，不看过程」**
- 中间 tool call、思考链、错误尝试均不可见，父 Agent 和用户都看不到
- 无法及时指出问题（同步阻塞）
- 💡 替代方案：Profile 多进程模式（如音/思月作为独立 Agent 跑飞书），代价是生命周期不再是「用完即走」

#### 需求④：用后自动释放 + 父代理总结写回 ✅部分支持

- **自动释放** ✅ 原生支持，子 Agent 返回后自动销毁
- **写回机制** ❌ 子 Agent 返回的是自报告（self-report），不一定准确
- **写入 soul 和 memory** ✅ 父 Agent 可调用 `memory`/`skill_manage` 工具，需写标准流程 skill

#### 总体结论

| 需求 | 原生支持度 | 定制量 |
|------|-----------|--------|
| ① 自动分解编排 | ⚡ 半自动 | 写编排 skill |
| ② 选 soul+skill+memory | 🛠 手动可做 | 写 context 映射逻辑 |
| ③ 过程对用户可见 | ❌ 不支持 | 换 Profile 模式或自研 |
| ④ 释放+写回总结 | ✅ 部分支持 | 写总结回写 skill |

**核心结论：** Hermes 提供了优秀的构建块（delegate_task、Profiles、memory、skills），但无开箱即用的「自动多 Agent 编排框架」。

#### 推荐路线

最接近愿景的组合：**父 Agent（编排者）+ Kanban（异步工作流编排）+ Profile 多进程（独立 soul+memory）**，而非 `delegate_task`。
