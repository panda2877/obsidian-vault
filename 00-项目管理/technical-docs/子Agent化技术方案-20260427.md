## 一、背景与目标

### 1.1 背景

老大对 Hermes Agent 的**子Agent委托模式**感兴趣，想研究能否把现有的三位姐妹（紫灵、如音、思月）从 **skill** 形态转化为**子Agent**。

现有三位姐妹：
- **紫灵**：需求/创意专家（skill）
- **幸如音**：技术专家（skill）
- **文思月**：文档专家（skill）

通过 `send_message` 工具调用，和银月共享同一个 Hermes 进程。

### 1.2 目标

分析 skill 和子Agent的差异，评估转化可行性，给出推荐方案。

---

## 二、现有架构分析

### 2.1 Skill 模式（当前）

```
银月（主Agent）
  │
  ├── send_message → 紫灵（skill）
  ├── send_message → 如音（skill）
  └── send_message → 思月（skill）

所有姐妹共享银月的进程、上下文、工具集
```

**特点**：
- 姐妹们是 SKILL.md 文件，加载到银月的上下文
- 通过 `send_message` 工具和银月通信
- 共享银月的工具集（terminal、read_file 等全部可用）
- 无独立预算限制

### 2.2 子Agent模式（Hermes 原生）

```
银月（主Agent）
  │
  └── delegate_task → 子Agent（如音/紫灵/思月）
                      - 独立上下文
                      - 独立50轮预算
                      - 禁用5个工具：delegate_task/clarify/memory/send_message/execute_code
```

**特点**：
- fork 新 AIAgent，独立上下文
- 独立 50 轮预算（父 Agent 90 轮）
- 父子只通过任务描述（传入）和最终摘要（传出）通信
- **禁用 send_message**：子Agent不能直接和银月/老大沟通

---

## 三、Skill vs 子Agent 核心差异

| 维度 | Skill 模式 | 子Agent 模式（delegate_task） |
|------|-----------|-------------------------------|
| **通信方式** | `send_message`（随时可发） | 只能通过 task 输入/输出，无法主动发消息 |
| **预算** | 共享父Agent预算 | 独立 50 轮 |
| **深度** | 无限制（skill 可嵌套 skill） | 仅 1 层（子不能再委托） |
| **并发** | 无限制 | 上限 3 个 |
| **工具禁用** | 无（共享全部工具） | 禁用 5 个：delegate_task/clarify/memory/send_message/execute_code |
| **上下文** | 共享父Agent上下文 | 独立上下文，父只看到最终摘要 |
| **适用场景** | 持续协作、顾问角色 | 独立任务、并行执行 |

---

## 四、核心矛盾分析

### 4.1 send_message 被禁用

子Agent 模式下，**send_message 是被禁用的 5 个工具之一**。

这意味着：
- 子Agent **不能**通过 `send_message` 主动找银月沟通
- 子Agent **不能**把结果直接发送给老大（微信）
- 只能通过 `delegate_task` 的返回值（摘要）传递给父Agent

**矛盾**：姐妹们的工作模式是「被银月召唤 → 干活 → 回复银月」，需要双向通信。如果转为子Agent，单向通信会破坏这个协作模式。

### 4.2 不能反问用户（clarify 被禁用）

子Agent 不能调用 `clarify`，意味着：
- 子Agent 在推理过程中**不能反问用户**澄清需求
- 紫灵擅长「多轮提问挖掘需求」的工作流会失效
- 如音遇到技术卡点时不能反问老大确认

### 4.3 不能写共享记忆（memory 被禁用）

子Agent 不能写共享记忆：
- 思月的文档归档记录无法持久化
- 姐妹们的上下文无法累积

## 五、可行方案

### 5.1 方案A：保持 Skill 模式（推荐）

**结论**：当前阶段不转化，维持现状。

**理由**：
1. 姐妹们的协作模式（双向通信、持续顾问）**天然不适合** delegate_task 的单向通信模型
2. `send_message` 是姐妹们工作的核心工具，被禁用后工作流断裂
3. Skill 模式在当前场景下运行良好，无明显痛点
4. 子Agent 的优势（独立预算、隔离上下文）对于姐妹们的场景**收益有限**

**适用场景**：姐妹们的角色是「专家顾问」，不是「独立任务执行器」。

### 5.2 方案B：Hermes 进程级子Agent（独立进程）

**核心思路**：不通过 `delegate_task`，而是通过**独立 Hermes 进程**实现子Agent。

**架构**：
```
银月（主会话）
  │
  ├── terminal → 启动 紫灵 独立进程（tmux/hermes chat）
  ├── terminal → 启动 如音 独立进程
  └── terminal → 启动 思月 独立进程

每个姐妹是独立 Hermes 进程，有独立上下文
通过共享文件/数据库通信
```

**实现方式**（参考 hermes-agent skill）：
```bash
# 启动独立如音进程
tmux new-session -d -s xingruyin -x 120 -y 40 'hermes -p xingruyin'

# 通过 tmux 发送任务
tmux send-keys -t xingruyin '帮我分析xxx技术问题' Enter

# 读取结果
tmux capture-pane -t xingruyin -p
```

**优势**：
- 真正的进程隔离
- 不受 delegate_task 的 5 个工具限制
- 可独立运行数小时/数天

**劣势**：
- 架构复杂，需要协调多进程通信
- 需要解决：任务分发、结果收集、状态管理
- 当前无现成框架，需要自行开发协调层

### 5.3 方案C：混合模式（未来方向）

**核心思路**：
- **日常协作**：保持 skill 模式，通过 `send_message` 沟通
- **重型任务**：对于复杂独立任务，使用**方案B**的独立进程模式

**适用场景**：
- 紫灵需要深入调研竞品 → 启动独立进程，结果写入 wiki
- 如音需要排查紧急故障 → 保持 skill 模式，实时沟通
- 思月需要批量归档文档 → 启动独立进程，自动处理

## 六、方案B 详细设计（独立进程子Agent）

### 6.1 架构设计

```
┌─────────────────────────────────────────────────────────┐
│                     银月（主会话）                        │
│  - 协调调度                                               │
│  - 任务分发                                               │
│  - 结果汇总                                               │
└─────────────────────────────────────────────────────────┘
        │                    │                    │
   ┌────┴────┐          ┌────┴────┐          ┌────┴────┐
   │ 紫灵进程 │          │ 如音进程 │          │ 思月进程 │
   │(tmux)   │          │(tmux)   │          │(tmux)   │
   │ hermes  │          │ hermes  │          │ hermes  │
   │ -p xing │          │ -p xing │          │ -p siy  │
   └─────────┘          └─────────┘          └─────────┘
        │                    │                    │
        └────────────────────┼────────────────────┘
                             │
                    ┌────────┴────────┐
                    │  共享存储层      │
                    │  - 任务队列      │
                    │  - 结果文档      │
                    │  - Obsidian Vault│
                    └─────────────────┘
```

### 6.2 任务队列设计

```markdown
# 任务队列格式（JSON Lines）

任务队列文件：`~/.hermes/agent-queue/tasks.jsonl`

{"id": "task-001", "agent": "xingruyin", "prompt": "分析XX技术方案", "status": "pending", "created": "2026-04-27T15:00:00"}
{"id": "task-002", "agent": "ziling", "prompt": "调研竞品YY", "status": "done", "result": "结论...", "completed": "2026-04-27T15:30:00"}
```

### 6.3 Agent 配置

每个姐妹的独立进程使用独立的 Hermes Profile：
```bash
# 如音进程
hermes -p xingruyin -w

# 紫灵进程
hermes -p ziling -w

# 思月进程
hermes -p siyue -w
```

Profile 隔离通过 `HERMES_HOME` 环境变量实现。

### 6.4 通信协议

```bash
# 1. 银月写入任务
echo '{"id": "task-001", "agent": "xingruyin", "prompt": "..."}' >> ~/.hermes/agent-queue/tasks.jsonl

# 2. 子Agent 读取任务（定时轮询或 inotify）
tail -n 1 ~/.hermes/agent-queue/tasks.jsonl | jq -r '.prompt'

# 3. 子Agent 执行并写入结果
echo '{"id": "task-001", "status": "done", "result": "..."}' >> ~/.hermes/agent-queue/results.jsonl

# 4. 银月读取结果
cat ~/.hermes/agent-queue/results.jsonl | jq '.id == "task-001"'
```

### 6.5 启动脚本

```bash
#!/bin/bash
# start-agents.sh - 启动所有姐妹独立进程

AGENTS=("xingruyin" "ziling" "siyue")

for agent in "${AGENTS[@]}"; do
    # 检查是否已运行
    if ! tmux has-session -t "$agent" 2>/dev/null; then
        echo "启动 $agent..."
        tmux new-session -d -s "$agent" -x 120 -y 40 "hermes -p $agent -w"
        sleep 3
    else
        echo "$agent 已运行"
    fi
done

echo "所有 Agent 已就绪"
```

## 七、风险与挑战

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 多进程协调复杂度高 | 实现成本大 | 先用方案A，方案B作为长期目标 |
| 任务队列可靠性 | 任务可能丢失 | 使用数据库替代文件（SQLite） |
| 子Agent 通信延迟 | 实时性差 | 设计超时机制，结果落盘后立即通知 |
| Profile 配置同步 | 配置不一致 | 集中管理配置模板，定期同步 |
| 进程管理复杂 | 运维成本高 | 使用 systemd 管理进程生命周期 |

## 八、结论与建议

### 8.1 结论

1. **短期**：姐妹们不适合转化为 `delegate_task` 子Agent
   - `send_message` 被禁用会破坏协作模式
   - `clarify` 被禁用会影响紫灵的需求挖掘流程

2. **中期**：可以考虑**独立进程子Agent**（方案B）
   - 不受 5 个工具限制
   - 实现真正的进程隔离
   - 需要开发协调层

3. **长期**：**混合模式**是最终目标
   - 日常协作保持 skill
   - 重型任务使用独立进程

### 8.2 下一步行动

| 优先级 | 行动 | 说明 |
|--------|------|------|
| P0 | 维持现状 | 继续使用 skill 模式，暂无转化必要 |
| P1 | 文档归档 | 本方案归档至 technical-docs |
| P2 | 方案验证 | 如老大有需求，可试点独立进程模式 |
