## 一、背景与目标

### 1.1 背景

老大对 Hermes Agent 的子Agent模式感兴趣，想研究能否把现有的三位姐妹（紫灵、如音、思月）从 **skill** 形态转化为**独立Agent**。

现有三位姐妹：
- **紫灵**：需求/创意专家（skill）
- **幸如音**：技术专家（skill）
- **文思月**：文档专家（skill）

通过 `send_message` 工具调用，和银月共享同一个 Hermes 进程。

### 1.2 目标

1. 实现**真正的人格隔离** — 四个人格独立，不混合
2. 支持**多平台接入** — 微信、飞书等多渠道
3. 实现**姐妹间通信可见** — 老大能看到讨论过程

---

## 二、Skill 模式的核心痛点

### 2.1 问题描述

Skill 模式下，四个人格会**混合在同一个执行者（银月）身上**：

| 问题 | 说明 |
|------|------|
| **人格混合** | 加载如音的 Skill，但说话者仍是银月，只是多了如音的知识/规范 |
| **语气趋同** | 如音会叫「宝子」（银月语气），思月会卖萌——但执行者都是银月 |
| **无法真正隔离** | Skill 只是「知识/指令」，不是独立的「人格实体」 |

### 2.2 老大的判断

> 「人格区分很重要」—— 老大明确

---

## 三、多Agent 方案优势

| 优势 | 说明 |
|------|------|
| **真正的人格隔离** | 每个 Agent 是独立进程，有自己初始化好的人格设定 |
| **语气/风格独立** | 如音内敛沉稳，思月严谨细致，紫灵活泼外放——互不干扰 |
| **无工具限制** | Profile 进程完全独立，所有工具可用（包括被禁用的 5 个） |
| **无预算限制** | 不受 50 轮限制 |

## 四、Profile 机制解析

### 4.1 核心架构

```
~/.hermes/
├── config.yaml                         # 主配置
├── .env                              # API keys
├── skills/                            # 技能
├── sessions/                          # 会话历史
├── memory/                            # 记忆
└── profiles/                          # 其他 profile（隔离）
    ├── xingruyin/                     # 如音 profile
    ├── ziling/                        # 紫灵 profile
    └── siyue/                        # 思月 profile
```

### 4.2 Profile 隔离性

| 维度 | 隔离程度 |
|------|---------|
| **配置文件** | ✅ 完全隔离（独立 config.yaml） |
| **技能 (skills/)** | ✅ 完全隔离 |
| **会话 (sessions/)** | ✅ 完全隔离（独立历史） |
| **记忆 (memory/)** | ✅ 完全隔离 |
| **进程** | ✅ 完全独立进程 |

### 4.3 与 delegate_task 的关键区别

| 维度 | delegate_task | Profile 多进程 |
|------|--------------|---------------|
| **进程** | 共享父进程 | **完全独立进程** |
| **上下文** | 父子共享 | **完全隔离** |
| **工具限制** | 5 个工具被禁用 | **✅ 无限制** |
| **预算** | 50 轮限制 | **✅ 无限制** |

## 五、多平台方案（飞书 + 微信）

### 5.1 需求分析

老大提出两个多平台需求：

| 需求 | 说明 |
|------|------|
| **会话接续** | 微信的会话能在飞书接上，不需要同步上下文，只需要连续对话 |
| **姐妹可见** | 姐妹们之间的讨论能在飞书群里展示出来 |

### 5.2 会话接续方案

**核心思路**：session 与 user 绑定，而非 channel 绑定。

| 当前状态 | 问题 |
|---------|------|
| session 按 channel 隔离 | 微信一个 session，飞书一个 session，互不相干 |
| session 按 user 绑定 | 同一个 user，无论哪个 channel，都接入同一个 session |

**实现步骤**：
1. 飞书开放平台创建应用，获取 app_id/app_secret
2. 配置 Hermes 连接飞书
3. 验证宝子在飞书和微信的 user_id 一致
4. 测试跨平台 session 是否接续

**待确认**：当前 Hermes Gateway 是否支持 user_id 跨 channel 绑定，需要实测。

### 5.3 飞书群聊协作方案

**目标**：姐妹们在飞书群里讨论，宝子能全程看到。

**方案架构**：

```
┌─────────────────────────────────────────────────────────┐
│                     飞书群                               │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐      │
│  │  宝子   │  │  银月   │  │  如音   │  │  紫灵   │      │
│  └─────────┘  └─────────┘  └─────────┘  └─────────┘      │
│                                              ┌─────────┐ │
│                                              │  思月   │ │
│                                              └─────────┘ │
└─────────────────────────────────────────────────────────┘
```

**实施步骤**：

| 阶段 | 步骤 | 说明 |
|------|------|------|
| **准备** | 创建飞书应用 | 在飞书开放平台创建自建应用，启用机器人能力 |
| **连接** | 配置 Hermes + 飞书 | 让 Hermes 能收发飞书消息 |
| **建群** | 创建飞书群 | 把宝子 + 银月 + 姐妹们都拉进去 |
| **配置** | 调整路由 | 让姐妹们的消息发到群里可见 |

**关键前提**：
- 飞书应用需要「机器人」能力
- 需要把应用添加到群里
- 每个姐妹需要有飞书账号（或统一使用一个飞书机器人账号）

### 5.4 多平台下的问题

| 问题 | 说明 |
|------|------|
| **姐妹账号** | 姐妹们需要有飞书账号，或者共用一个机器人账号 |
| **消息路由** | 需要明确哪些消息发到群里，哪些私聊 |
| **人格一致性** | 飞书群里姐妹们也要保持各自的人格特点 |

### 7.5 已知问题与排查

**问题1：飞书 app_id 冲突**

症状：`Gateway hit a non-retryable startup conflict: feishu: Another local Hermes gateway is already using this Feishu app_id (PID xxx)`

原因：两个 profile 配置了相同的 `FEISHU_APP_ID`

解决：确认每个 profile 的 `.env` 使用独立的飞书 app_id，重启报错的 gateway

验证：
```bash
cat ~/.hermes/profiles/wensiyue/.env | grep FEISHU_APP_ID
cat ~/.hermes/profiles/xingruyin/.env | grep FEISHU_APP_ID
# 两个值必须不同
```

**问题2：微信 token 冲突**

症状：`Weixin bot token already in use (PID xxx). Stop the other gateway first.`

原因：微信 bot token 只能被一个 gateway 进程使用

解决：只有银月的 gateway 连接微信，其他姐妹用飞书通信

**问题3：gateway_state.json 显示旧 PID**

症状：`gateway_state.json` 中的 PID 已不存在，但进程实际在运行

原因：gateway_state.json 是启动时的快照，不会实时更新，属正常行为，非故障

风险预案：以实际进程状态为准，用 `ps aux | grep hermes_cli.main` 验证。进程存在且 listen 端口正常 = 正常运行，无需处理

如需获取真实 PID：
```bash
cat ~/.hermes/profiles/{name}/gateway_state.json | python3 -c "import json,sys; d=json.load(sys.stdin); import os; pid=d.get('pid'); print(f'快照PID: {pid}, 进程存活: {os.path.exists(f\"/proc/{pid}\") if pid else \"N/A\"}')"
```

**问题4：重启后银月失忆**

现象：重启 gateway 后，银月不记得之前干了什么

缓解措施：重要操作前主动更新 memory 记录当前任务进度

## 八、协同流程

### 8.1 任务分发

```
银月：创建任务文件 → 通过 tmux 通知姐妹有新任务
姐妹：读取任务文件 → 执行 → 写结果文件 → 通过 send_message 通知银月
银月：读取结果文件 → 汇总给老大
```

### 8.2 飞书群聊模式

```
宝子（在群里发消息）
    ↓
银月（接收）
    ↓ 分派任务
如音/紫灵/思月（在群里回复）
    ↓
宝子看到所有讨论过程
```

## 九、消耗问题与解决思路

### 9.1 问题描述

多Agent方案相比 Skill 模式，**API 调用次数可能增加**：
- 每个 Agent 独立推理
- 协调层（银月）需要额外的路由/分发调用

### 9.2 解决思路

| 方向 | 具体措施 |
|------|---------|
| **减少不必要的调用** | 明确什么时候该调用 Agent，避免「凡事都问姐妹」 |
| **控制对话轮次** | 任务一次性说清楚，减少来回追问 |
| **合并任务** | 多个小任务合并为一个批次，分摊调用成本 |
| **按需启用** | 不是所有场景都需要多Agent，简单任务银月直接处理 |
