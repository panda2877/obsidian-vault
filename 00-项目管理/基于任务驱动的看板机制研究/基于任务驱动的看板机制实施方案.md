# 基于任务驱动的看板机制实施方案

> 本文档为技术研究文档，源自与银月的讨论。
> 研究目标：结合记忆快照机制与看板思路，设计一套适合多 Hermes profile 协作的长期记忆与任务协同方案。

---

## 一、背景与问题陈述

### 1.1 现有方案

**记忆快照机制（Snapshot）**

- 核心逻辑：会话结束时将整个消息状态打包为 JSON 快照文件，新会话启动时注入 system prompt
- 存储位置：`~/.hermes/memory/snapshot/`
- 关键特性：
  - `atexit` 进程级兜底（SIGTERM/SIGINT/正常退出时触发快照写入）
  - 正则解析出 `task_goals`、`checklist`、`assignments`、`missing_info`
  - Schema v2，支持 unfinished 快照优先加载
- 解决的问题：单 agent 跨 session 的上下文不丢失
- 未解决的问题：多 agent 协同、任务状态可视化、人工干预

**看板机制（Kanban）**

- Hermes v0.12 引入，任务状态存储于 SQLite，看板界面支持拖拽
- 核心组件：`TaskBoard`、`KanbanBoard`、`useTaskStore`（Zustand）
- 任务状态： inbox → assigned → in_progress → review → done
- 新增能力：多 agent 并行拉取任务、missionId 隔离、Review gate 自动审批

### 1.2 两种方案的核心差异

| 维度 | 快照（Snapshot） | 看板（Kanban） |
|------|-------------------|----------------|
| 存储介质 | JSON 文件 | SQLite |
| 状态粒度 | 整个会话 | 单个任务 |
| 多 agent 感知 | ❌ | ✅ missionId 隔离 |
| 上下文完整性 | ✅ 被动全量保存 | ⚠️ 依赖主动写入 |
| 人工干预 | 需要透传 | 直接改看板 |
| 失败恢复 | ✅ 上下文完整恢复 | ⚠️ 需要 write_context 机制 |

### 1.3 关键洞察

**看板方案在「上下文不丢失」上弱于快照。**

如果 agent 在任务中途崩溃（且没有主动 write_context）：
- 看板只知道「任务在 in_progress」
- 但 agent 之前做了哪些决策、试了什么方法、哪里卡住——全部丢失

快照的保障是「被动」的：进程退出前自动捕获整个消息状态。

看板的保障是「主动」的：依赖 agent 在任务阶段变更时主动写入上下文。

---

## 二、设计目标

1. **保留快照的上下文保障**：不丢失任何工作进度
2. **引入看板的多 agent 协同能力**：任务状态可见、可追踪、可干预
3. **设计checkpoint机制**：解决看板在失败恢复上的弱点
4. **与现有 Hermes Snapshot 插件共存**：不依赖 v0.12，独立实现

---

## 三、整体架构

### 3.1 核心组件

```
┌─────────────────────────────────────────────────────┐
│                    看板存储层（SQLite）              │
│  ┌─────────────┐  ┌──────────────┐  ┌───────────┐  │
│  │  Task 表    │  │ Checkpoint 表 │  │ Agent 表  │  │
│  │  任务状态   │  │  阶段上下文   │  │  agent 注册│  │
│  └─────────────┘  └──────────────┘  └───────────┘  │
└─────────────────────────────────────────────────────┘
                          ↑
┌─────────────────────────────────────────────────────┐
│                   Hook 触发层                        │
│  on_task_start   on_phase_change   on_task_done    │
└─────────────────────────────────────────────────────┘
                          ↑
┌─────────────────────────────────────────────────────┐
│              Snapshot Memory Provider               │
│  （改造以支持看板协同模式）                          │
└─────────────────────────────────────────────────────┘
```

### 3.2 数据模型

**Task 表**
```sql
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  description TEXT,
  column TEXT NOT NULL DEFAULT 'backlog',
  priority TEXT NOT NULL DEFAULT 'normal',
  assignee TEXT,
  mission_id TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

**Checkpoint 表**
```sql
CREATE TABLE checkpoints (
  id TEXT PRIMARY KEY,
  task_id TEXT NOT NULL,
  phase TEXT NOT NULL,
  summary TEXT,
  blockers TEXT,
  next_steps TEXT,
  agent_id TEXT,
  created_at TEXT NOT NULL,
  FOREIGN KEY (task_id) REFERENCES tasks(id)
);
```

## 四、关键设计决策

### 4.1 看板负责什么

- **任务状态**（哪列、谁负责、优先级）
- **阶段推进**（backlog → in_progress → review → done）
- **人工干预入口**（拖拽、修改优先级、重新分配）

### 4.2 快照/checkpoint 负责什么

- **工作上下文**（阶段发现、决策、卡点）
- **阶段间的上下文**（下一个 agent 接手时能完整恢复）
- **缺失信息标记**（需要在什么地方补充）

### 4.3 崩溃恢复保障

**触发时机**：任务状态变更时（如 in_progress → review）

**写入内容**：
```python
{
    "phase": "implementing",
    "findings": ["payment API documented", "webhook endpoint confirmed"],
    "blockers": ["缺少沙箱密钥"],
    "next_steps": ["等密钥到位后继续测试对账逻辑"]
}
```

**恢复时**：新 agent 拉取任务时，同时读取最新的 checkpoint，还原上下文。

### 4.4 与 Snapshot 插件的整合

现有 Snapshot 插件的 `context_extractor.py` 提供了正则解析能力（`extract_task_context`），可以复用：
- `task_goals` → 作为任务标题/描述来源
- `checklist` → 作为子任务/里程碑
- `missing_info` → 作为 checkpoint 的 blockers

改造思路：
1. Snapshot Provider 在 `on_session_end` 时，写入快照文件**同时**，检查是否存在看板任务关联
2. 如果存在看板任务关联，写入 checkpoint
3. 新会话启动时，优先从 checkpoint 恢复上下文，而不是从快照全文注入

## 五、里程碑计划

### 里程碑 1：生成实施方案（本文件）
- 状态：✅ 完成

### 里程碑 2：制定看板文件范式
- 输出：`看板文件范式.md`
- 内容：
  - Obsidian 看板的目录结构规范
  - 每个任务对应的 Markdown 文件格式（含 checkpoint 嵌入格式）
  - 与 SQLite 的对应关系说明

### 里程碑 3：修改现有 Snapshot 机制代码 ✅
- 文件：
  - `plugins/memory/snapshot/provider.py` ✅
  - `plugins/memory/snapshot/context_extractor.py`（无需修改，复用）
  - `plugins/memory/snapshot/snapshot_store.py`（无需修改）
  - `plugins/memory/snapshot/checkpoint_store.py` ✅ **新增**
- 改造点：
  - `initialize`：打开 CheckpointStore
  - `_flush_pending`：写快照同时写 checkpoint（从 extract_task_context 映射）
  - `_write_checkpoint`：将 task_goals/checklist/missing_info 映射为 phase/blockers/next_steps
  - `_format_snapshot_block`：注入 SQLite checkpoint 上下文
  - 公共 API：`write_checkpoint()`、`get_latest_checkpoint()`、`get_mission_checkpoints()`
  - 阶段判定：`finished=true` → `wrapping`，否则 `implementing`

### 里程碑 4：落地看板触发 Hook ⏳ 进行中
- 实现：
  - `on_task_start(task_id, agent_id)` → 调用 `write_checkpoint(phase='exploring')`
  - `on_phase_change(task_id, from, to)` → 调用 `write_checkpoint(phase=<阶段>)`
  - `on_task_done(task_id)` → 调用 `write_checkpoint(phase='done')`
- **注意**：Hook 的集成需要修改 `run_agent.py` 的主循环回调，这部分需要在 Hermes Agent 主循环中实现，当前 checkpoint_store.py 和 provider.py 的公共 API 已就绪

## 六、风险与备选

### 6.1 SIGKILL 盲区

atexit 无法覆盖 SIGKILL/OOM，这是 Snapshot 的固有限制，看板方案同样存在。
备选：定期写入 checkpoint（如每 N 轮对话后），降低单次崩溃的丢失量。

### 6.2 多 agent 并发写同一任务

看板状态变更如果并发写入，可能存在竞态。
备选：SQLite 事务锁，或引入乐观锁（version 字段）。

### 6.3 不用 Hermes v0.12

自己实现看板机制需要独立维护 SQLite schema 和 hook 逻辑，增加维护成本。
备选：持续关注 Hermes v0.12 发布，如有重大架构变更重新评估。

### 7.2 参考讨论

本方案源自 2026-05-04 与银月的讨论，核心结论：
- 看板 + checkpoint 结合是可行的
- 不能用看板完全替代快照，上下文完整性需要独立保障
- 触发点从「进程退出」变为「任务阶段变更」
