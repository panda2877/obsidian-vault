# 基于任务驱动的看板机制实施方案

> 本文档为技术实施主文档，修订时间：2026-05-04
> 研究目标：结合记忆快照机制与看板思路，设计一套适合多 Hermes profile 协作的长期记忆与任务协同方案。
> 策略：不做迁移，做嫁接 — 保留自建逻辑，复用原生实现

---

## 一、现状与问题

### 1.1 两套 DB 并存

| | 自建方案（原有） | 原生 v0.12 |
|--|---------|------------|
| DB 路径 | `~/.hermes/kanban/tasks.db` | `~/.hermes/kanban.db` |
| 状态机 | backlog/inbox/assigned/in_progress/review/done | triage/todo/ready/running/blocked/done/archived |
| 并发安全 | 无（connect→execute→close，无事务） | WAL + BEGIN IMMEDIATE |
| 任务历史 | ❌ 无 | ✅ task_runs（每次尝试完整记录） |
| 依赖链 | ❌ 无 | ✅ task_links |
| 上下文聚合 | ❌ 无 | ✅ build_worker_context |
| claim/心跳 | ❌ 无 | ✅ claim_lock + 15min TTL + heartbeat |
| 事件流 | ❌ 无 | ✅ task_events |
| agent 注册 | ✅ 有 | ❌ 无 |
| mission 维度 | ✅ 有 | ❌ 无（用 tenant 代替） |
| workspace | ❌ 无 | ✅ scratch/worktree/dir |

**核心问题**：两套 DB 完全隔离，状态分裂，多 agent 协同失效。

### 1.2 两种方案的核心差异

| 维度 | 快照（Snapshot） | 看板（Kanban） |
|------|-------------------|----------------|
| 存储介质 | JSON 文件 | SQLite |
| 状态粒度 | 整个会话 | 单个任务 |
| 多 agent 感知 | ❌ | ✅ missionId 隔离 |
| 上下文完整性 | ✅ 被动全量保存 | ⚠️ 依赖主动写入 |
| 人工干预 | 需要透传 | 直接改看板 |
| 失败恢复 | ✅ 上下文完整恢复 | ⚠️ 需要 checkpoint 机制 |

### 1.3 关键洞察

看板方案在「上下文不丢失」上弱于快照。如果 agent 在任务中途崩溃（且没有主动写 checkpoint），看板只知道「任务在 running」，但之前做了哪些决策、试了什么方法、哪里卡住——全部丢失。

快照的保障是「被动」的：进程退出前自动捕获整个消息状态。
看板的保障是「主动」的：依赖 agent 在任务阶段变更时主动写入上下文。

---

## 二、设计目标

1. **保留快照的上下文保障**：不丢失任何工作进度
2. **引入看板的多 agent 协同能力**：任务状态可见、可追踪、可干预
3. **设计 checkpoint 机制**：解决看板在失败恢复上的弱点
4. **统一 DB 路径到原生**：`~/.hermes/kanban.db`，不复用自建 DB
5. **复用原生实现**：并发安全、claim 锁、task_runs、build_worker_context

---

## 三、整合原则

**不做迁移，做嫁接。**

```
自建逻辑（保留）
├── agent 注册
├── mission 维度
├── 状态机映射（backlog→done ↔ 原生状态）
├── Obsidian frontmatter 同步
└── Checkpoint 表 + Hook 触发逻辑

嫁接原生（复用）
├── SQLite WAL + BEGIN IMMEDIATE（并发安全）
├── task_runs（尝试历史）
├── task_links（依赖链）
├── build_worker_context（上下文聚合）
├── claim_lock / heartbeat（分布式锁）
├── task_events（事件流）
└── hermes kanban CLI + kanban_tools 工具链
```

## 六、状态机映射

自建状态与原生状态的对应关系：

| 自建 | 原生 | 说明 |
|------|------|------|
| backlog | triage | 等进入看板队列 |
| inbox | todo | 人工整理阶段 |
| assigned | ready | 已分派，待认领 |
| in_progress | running | 执行中 |
| review | running | review 复用 running，语义由标记区分 |
| done | done | 完成 |
| — | blocked | 新增（人工干预入口） |
| — | archived | 新增（归档） |

```python
STATUS_MAP_TO_NATIVE = {
```

## 七、tasks_store.py 重构

### 7.1 改造思路

删掉所有自建 DB 底层操作，直接调用原生 `kanban_db.py`：
- 连接：`kanban_db.connect()`
- 事务：`kanban_db.write_txn()`
- 任务操作：调用原生 `create_task` / 直接执行 UPDATE 等

**保留**：
- Obsidian frontmatter 同步（`upsert_from_obsidian`）
- agent 注册（`register_agent` / `update_agent_status`）
- mission 维度映射
- 状态映射层

### 7.2 具体改造点

#### 连接层

```python
# 旧
conn = sqlite3.connect(str(_get_db_path()), timeout=10)

# 新
from hermes_cli import kanban_db as kb
conn = kb.connect()
```

#### 事务层

```python
# 旧
conn.execute(...)
conn.commit()

# 新
with kb.write_txn(conn):
    conn.execute(...)
```

#### create_task

```python
# 新：调用原生
kb.create_task(
    conn,
    title=title,
    body=description,
    assignee=assignee,
    tenant=mission_id,  # mission_id 映射到原生 tenant 字段
    triage=True,  # backlog 映射到 triage
    ...
)
```

#### update_task_status

```python
# 新：先映射状态，再调用原生
native_status = STATUS_MAP_TO_NATIVE.get(status, status)
with kb.write_txn(conn):
    conn.execute(
        "UPDATE tasks SET status = ?, updated_at = ? WHERE id = ?",
        (native_status, now, task_id)
    )
```

#### agent 注册

保留独立 `agent_registry` 表，不借用原生任何机制。

#### Checkpoint 操作

独立保留，路径指向原生 kanban.db 里的 Checkpoint 表。

## 八、Checkpoint 机制

### 8.1 触发时机

| 事件 | 触发 |
|------|------|
| `agent:start` | 读取最新 checkpoint，还原上下文 |
| `agent:end` | 写入 checkpoint（从 `finished=true` 判断） |
| 任务状态变更 | 通过 Hook 系统触发 |

### 8.2 Checkpoint 内容

```python
{
    "phase": "implementing",   # 或 "wrapping"
    "findings": [...],        # 从 extract_task_context 映射
    "blockers": [...],        # 从 missing_info 映射
    "next_steps": [...]
}
```

### 8.3 与原生 task_runs 的区别

| | Checkpoint | 原生 task_runs |
|--|-----------|----------------|
| 粒度 | 阶段级（implementing/wrapping） | 尝试级（一次 running 即一条记录） |
| 内容 | findings/blockers/next_steps | summary/metadata/error |
| 触发 | agent:end + phase_change Hook | claim → complete/block |
| 用途 | 跨阶段上下文恢复 | 跨尝试历史追溯 |

两者互补，不冲突。

## 十二、风险与备选

### 12.1 mission_id vs tenant

原生用 `tenant` 字段做多租户隔离。自建方案用 `mission_id`。映射关系：
- `task.mission_id` → 写入原生 `task.tenant`
- 查询时按 `tenant` 过滤 = 按 `mission_id` 过滤

### 12.2 自建状态丢失

状态映射到原生后，原生状态（如 `blocked`）无法映射回自建状态。**这是可接受的**：新状态是原生的增强，自建方案向原生靠拢。

### 12.3 并发安全

直接复用原生 WAL + BEGIN IMMEDIATE，无需自建锁机制。

### 12.4 SIGKILL 盲区

atexit 无法覆盖 SIGKILL/OOM，这是 Snapshot 的固有限制，看板方案同样存在。
备选：定期写入 checkpoint（如每 N 轮对话后），降低单次崩溃的丢失量。

## 十三、里程碑层级 — 新增字段与数据模型

> 里程碑看板前端已从二层（里程碑→任务）重构为三层（项目→里程碑→任务）。当前 BFF 从 SQLite tasks 表通过 `[Mx]` 前缀正则解析里程碑聚合，**但 SQLite tasks 表没有显式的里程碑字段**，导致：
> - 无法为单个任务指定跨里程碑标签
> - 无法为任务排序（目前依赖 `created_at DESC`）
> - 无法独立查询里程碑元信息（描述、负责人、截止日期等）
> - 前端需要 `project_name` 来分组，但 tasks 表的 `project_name` 字段未用于 BFF milestone 查询

### 13.1 新增表：milestones

新增独立的 `milestones` 表，与 `tasks` 表通过 `milestone_id` 关联：

```sql
CREATE TABLE IF NOT EXISTS milestones (
    id          TEXT PRIMARY KEY,              -- 如 'M1', 'M2', 'M3'
    project_name TEXT NOT NULL,                -- 关联 project（如 'hermes多功能看板'）
    name        TEXT NOT NULL,                 -- 如 'M1 — 选取前端框架'
    description TEXT,                          -- 可选：里程碑描述
    assignee    TEXT,                          -- 负责人
    target_date TEXT,                          -- 目标日期（可选）
    sort_order  INTEGER DEFAULT 0,            -- 排序权重（M1=1, M2=2...）
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER
);
CREATE INDEX IF NOT EXISTS idx_milestones_project ON milestones(project_name);
```

### 13.2 新增字段：milestone_id（tasks 表）

```sql
ALTER TABLE tasks ADD COLUMN milestone_id TEXT REFERENCES milestones(id);
ALTER TABLE tasks ADD COLUMN milestone_sort INTEGER DEFAULT 0;
```

**`milestone_sort`** 用于里程碑内任务排序（替代目前依赖 `created_at DESC`），允许手动调整任务顺序。

### 13.3 数据关系图

```
projects（逻辑层，非表）
    │
    ├── milestones 表
    │       │
    │       └── tasks 表（通过 milestone_id 关联）
    │
    └── tasks 表（无 milestone_id 的任务 = 未分组）
```

### 13.4 迁移策略

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 创建 `milestones` 表 | 通过 `init_custom_tables()` 或 SQL 脚本 |
| 2 | 新增 `milestone_id` + `milestone_sort` 列 | `ALTER TABLE` 幂等操作 |
| 3 | 从现有数据回填 | 从 tasks 标题 `[Mx]` 前缀解析，自动创建 milestones 记录并关联 |
| 4 | 验证 | BFF milestone.js 改用 milestones 表 + milestone_id 关联，替代标题正则解析 |

### 13.5 回填脚本（一次性）

```python
# 从现有 tasks 的 [Mx] 前缀自动创建 milestones 记录并回填 milestone_id
import sqlite3, re, time

db = "/home/agentuser/.hermes/kanban.db"
conn = sqlite3.connect(db)
cur = conn.cursor()

# 1. 确保 milestones 表存在
cur.execute("""
    CREATE TABLE IF NOT EXISTS milestones (
        id TEXT PRIMARY KEY,
        project_name TEXT NOT NULL,
        name TEXT NOT NULL,
        description TEXT,
        assignee TEXT,
        target_date TEXT,
        sort_order INTEGER DEFAULT 0,
        created_at INTEGER NOT NULL,
        updated_at INTEGER
    )
""")

# 2. 确保 milestone_id + milestone_sort 列存在
cols = [r[1] for r in cur.execute("PRAGMA table_info(tasks)").fetchall()]
if 'milestone_id' not in cols:
    cur.execute("ALTER TABLE tasks ADD COLUMN milestone_id TEXT REFERENCES milestones(id)")
if 'milestone_sort' not in cols:
    cur.execute("ALTER TABLE tasks ADD COLUMN milestone_sort INTEGER DEFAULT 0")

# 3. 按 project_name 分组，从 tasks 解析 [Mx] 前缀
for pn, in cur.execute("SELECT DISTINCT project_name FROM tasks WHERE project_name IS NOT NULL AND project_name != ''"):
    # 获取该项目的所有任务
    tasks = cur.execute(
        "SELECT id, title FROM tasks WHERE project_name = ? ORDER BY id",
        (pn,)
    ).fetchall()

    # 解析 [Mx] 和 [Mx.y] 前缀，建立里程碑映射
    milestone_tasks = {}  # major_key → [(task_id, title)]
    for tid, title in tasks:
        m = re.match(r'^\[M(\d+)(?:\.(\d+))?\]', title)
        if m:
            major = f"M{m.group(1)}"
            if major not in milestone_tasks:
                milestone_tasks[major] = []
            milestone_tasks[major].append((tid, title))

    # 创建里程碑记录并关联任务
    now = int(time.time())
    for major, task_list in sorted(milestone_tasks.items(),
                                   key=lambda x: int(x[0][1:])):
        # 推导里程碑名称
        name = None
        for tid, title in task_list:
            m2 = re.match(r'^\[M(\d+)\]\s*(.+)$', title)
            if m2:
                name = f"{major} — {m2.group(2).strip()}"
                break
        if not name:
            for tid, title in task_list:
                m2 = re.match(r'^\[M\d+\.\d+\]\s*(.+)$', title)
                if m2:
                    name = f"{major} — {m2.group(1).strip()}"
                    break
        if not name:
            name = major

        # upsert 里程碑记录
        sort_order = int(major[1:])
        cur.execute("""
            INSERT INTO milestones (id, project_name, name, sort_order, created_at)
            VALUES (?, ?, ?, ?, ?)
            ON CONFLICT(id) DO UPDATE SET
                name = excluded.name,
                project_name = excluded.project_name,
                sort_order = excluded.sort_order
        """, (major, pn, name, sort_order, now))

        # 回填 milestone_id 到 tasks
        for i, (tid, title) in enumerate(task_list):
            cur.execute(
                "UPDATE tasks SET milestone_id = ?, milestone_sort = ? WHERE id = ?",
                (major, i, tid)
            )

conn.commit()
conn.close()
print("Milestone migration complete.")
```

### 13.6 BFF 改动

`backend/services/milestone.js` 从标题正则解析改为 **JOIN milestones 表 + 读取 tasks.milestone_id**：

```javascript
function getMilestones() {
  const rows = sqlite.query(`
    SELECT
      t.id, t.title, t.status, t.priority, t.assignee,
      t.project_name, t.milestone_id, t.milestone_sort,
      m.name AS milestone_name, m.sort_order AS milestone_order
    FROM tasks t
    LEFT JOIN milestones m ON t.milestone_id = m.id
    WHERE t.project_name IS NOT NULL AND t.project_name != ''
    ORDER BY
      m.sort_order,
      t.milestone_sort,
      CASE t.status WHEN 'in_progress' THEN 0 ... END
  `)
  // 按 milestone_id 分组，milestone_name 从 milestones 表取
  // ...
}
```
