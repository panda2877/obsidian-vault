# 看板机制与原生 v0.12 整合方案

> 本文档为技术实施文档，修订时间：2026-05-04
> 目标：将自建看板方案与 Hermes v0.12 原生 kanban 机制整合，保留自建逻辑，复用原生实现

---

## 一、现状与问题

### 1.1 两套 DB 并存

| | 自建方案 | 原生 v0.12 |
|--|---------|------------|
| DB 路径 | `~/.hermes/kanban/tasks.db` | `~/.hermes/kanban.db` |
| 状态机 | backlog/inbox/assigned/in_progress/review/done | triage/todo/ready/running/blocked/done/archived |
| 并发安全 | 无（connect→execute→close，无事务） | WAL + BEGIN IMMEDIATE |
| 任务历史 | ❌ 无 | ✅ task_runs（每次尝试完整记录） |
| 依赖链 | ❌ 无 | ✅ task_links |
| 上下文聚合 | ❌ 无 | ✅ build_worker_context |
| claim/心跳 | ❌ 无 | ✅ claim_lock + 15min TTL + heartbeat |
| 事件流 | ❌ 无 | ✅ task_events |
| agent 注册 | ✅ 有 | ❌ 无 |
| mission 维度 | ✅ 有 | ❌ 无（用 tenant 代替） |
| workspace | ❌ 无 | ✅ scratch/worktree/dir |

**核心问题**：两套 DB 完全隔离，导致：
- 原生 `hermes kanban` CLI 看不到自建任务
- 原生 dispatcher 无法调度自建任务
- 状态分裂，多 agent 协同失效

---

## 二、整合原则

**不做迁移，做嫁接。**

```
自建逻辑（保留）
├── agent 注册
├── mission 维度
├── 状态机（backlog→done）
├── Obsidian frontmatter 同步（upsert_from_obsidian）
└── Checkpoint 表 + Hook 触发逻辑

嫁接原生（复用）
├── SQLite WAL + BEGIN IMMEDIATE（并发安全）
├── task_runs（尝试历史）
├── task_links（依赖链）
├── build_worker_context（上下文聚合）
├── claim_lock / heartbeat（分布式锁）
├── task_events（事件流）
└── hermes kanban CLI + kanban_tools 工具链
```

---

## 三、DB 路径统一

### 3.1 决策：弃用自建 DB，统一到原生路径

**旧（自建）**：`~/.hermes/kanban/tasks.db`
**新（原生）**：`~/.hermes/kanban.db`

统一到原生路径后：
- 所有 agent（不论 profile）共用同一份 DB
- 原生 CLI 和工具链直接可见
- 自建 Hook 和 Checkpoint 逻辑无需修改路径

### 3.2 操作

**第一步**：确认原生 kanban.db 已初始化

```python
from hermes_cli.kanban_db import connect, init_db
init_db()
```

**第二步**：在原生 `tasks` 表上加 `mission_id` 列

利用原生已有的迁移机制 `_migrate_add_optional_columns`，只需在 `kanban_db.py` 的迁移函数里追加即可：

```python
# kanban_db.py → _migrate_add_optional_columns()
if "mission_id" not in cols:
    conn.execute("ALTER TABLE tasks ADD COLUMN mission_id TEXT")
```

**第三步**：删除自建 `tasks_store.py`，不再独立维护 DB 连接

## 四、Schema 变更

### 4.1 新增列（通过迁移）

```sql
ALTER TABLE tasks ADD COLUMN mission_id TEXT;
```

### 4.2 Checkpoint 表（独立保留）

原生没有 Checkpoint 概念，这是自建方案的核心保障机制，保留在原生 kanban.db 中：

```sql
CREATE TABLE IF NOT EXISTS checkpoints (
    id          TEXT PRIMARY KEY,
    task_id     TEXT NOT NULL,
    phase       TEXT NOT NULL,
    summary     TEXT,
    blockers    TEXT,
    next_steps  TEXT,
    agent_id    TEXT,
    created_at  TEXT NOT NULL,
    FOREIGN KEY (task_id) REFERENCES tasks(id)
);
CREATE INDEX IF NOT EXISTS idx_checkpoint_task ON checkpoints(task_id);
```

### 4.3 Agent Registry 表（独立保留）

原生靠 profile 环境变量，没有显式 agent 注册表。自建方案需要保留：

```sql
CREATE TABLE IF NOT EXISTS agent_registry (
    id            TEXT PRIMARY KEY,
    profile       TEXT NOT NULL UNIQUE,
    name          TEXT NOT NULL,
    role          TEXT NOT NULL DEFAULT 'generalist',
    capabilities  TEXT NOT NULL DEFAULT '[]',
    status        TEXT NOT NULL DEFAULT 'idle',
    registered_at TEXT NOT NULL
);
```

## 五、状态机映射

自建状态与原生状态的对应关系：

| 自建 | 原生 | 说明 |
|------|------|------|
| backlog | triage | 等进入看板队列 |
| inbox | todo | 人工整理阶段 |
| assigned | ready | 已分派，待认领 |
| in_progress | running | 执行中 |
| review | running | review 仍算 running，保持上下文 |
| done | done | 完成 |
| — | blocked | 新增（人工干预入口） |
| — | archived | 新增（归档） |

**实现方式**：在 `tasks_store.py` 改造后，对外暴露自建状态枚举，内部转换为原生状态。

```python
# 状态映射表（自建 → 原生）
STATUS_MAP_TO_NATIVE = {
    "backlog": "triage",
    "inbox": "todo",
    "assigned": "ready",
    "in_progress": "running",
    "review": "running",  # 复用 running，review 语义由 column 标记
    "done": "done",
}

# 状态映射表（原生 → 自建）
STATUS_MAP_FROM_NATIVE = {
    "triage": "backlog",
    "todo": "inbox",
    "ready": "assigned",
    "running": "in_progress",
    "blocked": "in_progress",  # blocked 期间保持 in_progress
    "done": "done",
    "archived": "done",
}
```

## 六、tasks_store.py 重构

### 6.1 改造思路

删掉所有自建 DB 底层操作，直接调用原生 `kanban_db.py`：
- 连接：`kanban_db.connect()`
- 事务：`kanban_db.write_txn()`
- 任务操作：`kanban_db.create_task()` / `kanban_db.update_task()` 等

**保留**：
- Obsidian frontmatter 同步（`upsert_from_obsidian`）
- agent 注册（`register_agent` / `update_agent_status`）
- mission 维度映射（加 `mission_id` 到原生 tasks 表）
- 状态映射层

### 6.2 具体改造点

#### 连接层

```python
# 旧
conn = sqlite3.connect(str(_get_db_path()), timeout=10)

# 新
from hermes_cli import kanban_db as kb
conn = kb.connect()
```

#### 事务层

```python
# 旧
conn.execute(...)
conn.commit()

# 新
with kb.write_txn(conn):
    conn.execute(...)
```

#### create_task

```python
# 旧：自建 INSERT
conn.execute("""INSERT OR IGNORE INTO tasks ...""", (...))
conn.commit()

# 新：调用原生
kb.create_task(
    conn,
    title=title,
    body=description,
    assignee=assignee,
    tenant=mission_id,  # mission_id 映射到原生 tenant 字段
    triage=True,  # backlog 映射到 triage
    ...
)
```

#### update_task_status

```python
# 旧
conn.execute("UPDATE tasks SET status = ?, updated_at = ? WHERE id = ?", ...)

# 新：先映射状态，再调用原生
native_status = STATUS_MAP_TO_NATIVE.get(status, status)
kb.update_task(conn, task_id, status=native_status)
```

注：原生 `kanban_db` 没有 `update_task` 单一函数，需要在 `write_txn` 里直接执行 UPDATE，或新增辅助函数。

#### agent 注册

保留独立 `agent_registry` 表，不借用原生任何机制。

#### Checkpoint 操作

独立保留，路径指向原生 kanban.db 里的 Checkpoint 表。

## 七、Checkpoint 机制（保留）

### 7.1 触发时机

| 事件 | 触发 |
|------|------|
| `agent:start` | 读取最新 checkpoint，还原上下文 |
| `agent:end` | 写入 checkpoint（从 `finished=true` 判断） |
| `on_phase_change` | Hook 触发（待实现，依赖任务阶段检测） |

### 7.2 Checkpoint 内容

```python
{
    "phase": "implementing",   # 或 "wrapping"
    "findings": [...],        # 从 extract_task_context 映射
    "blockers": [...],        # 从 missing_info 映射
    "next_steps": [...]
}
```

### 7.3 与原生 task_runs 的区别

| | Checkpoint | 原生 task_runs |
|--|-----------|----------------|
| 粒度 | 阶段级（implementing/wrapping） | 尝试级（一次 running 即一条记录） |
| 内容 | findings/blockers/next_steps | summary/metadata/error |
| 触发 | agent:end + phase_change Hook | claim → complete/block |
| 用途 | 跨阶段上下文恢复 | 跨尝试历史追溯 |

两者互补，不冲突。

### Step 2：创建 Checkpoint + Agent 表

```python
from hermes_cli.kanban_db import connect

def init_custom_tables():
    conn = connect()
    conn.execute("""
        CREATE TABLE IF NOT EXISTS checkpoints (
            id TEXT PRIMARY KEY,
            task_id TEXT NOT NULL,
            phase TEXT NOT NULL,
            summary TEXT,
            blockers TEXT,
            next_steps TEXT,
            agent_id TEXT,
            created_at TEXT NOT NULL
        )
    """)
    conn.execute("""
        CREATE TABLE IF NOT EXISTS agent_registry (
            id TEXT PRIMARY KEY,
            profile TEXT NOT NULL UNIQUE,
            name TEXT NOT NULL,
            role TEXT NOT NULL DEFAULT 'generalist',
            capabilities TEXT NOT NULL DEFAULT '[]',
            status TEXT NOT NULL DEFAULT 'idle',
            registered_at TEXT NOT NULL
        )
    """)
    conn.close()
```

## 十二、风险与备选

### 12.1 mission_id vs tenant

原生用 `tenant` 字段做多租户隔离。自建方案用 `mission_id`。映射关系：
- `task.mission_id` → 写入原生 `task.tenant`
- 查询时按 `tenant` 过滤 = 按 `mission_id` 过滤

### 12.2 自建状态丢失

状态映射到原生后，原生状态（如 `blocked`）无法映射回自建状态。**这是可接受的**：新状态是原生的增强，自建方案向原生靠拢。

### 12.3 并发安全

直接复用原生 WAL + BEGIN IMMEDIATE，无需自建锁机制。
