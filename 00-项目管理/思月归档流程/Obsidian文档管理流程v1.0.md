## 3. 归档流程

### 3.1 如音移交（思月接收）

**情况一：跨项目技术文档**
适用于部署规范、技术标准等通用技术文档，不属于特定项目。

```
如音完成跨项目技术文档
    ↓
提供变更摘要：
  - 文档名称
  - 变更摘要（一句话）
  - 变更原因
  - 关联项目/需求（如有）
    ↓
思月归档到 ~/obsidian-vault/00-项目管理/technical-docs/
    ↓
更新 technical-docs/CHANGELOG.md
    ↓
手动 push 到 GitHub
    ↓
思月向银月汇报归档结果
```

**情况二：项目技术文档**
适用于有明确项目归属的技术方案。

```
如音完成项目技术文档
    ↓
提供变更摘要：
  - 文档名称
  - 所属项目
  - 关联需求编号（如有）
  - 变更摘要（一句话）
  - 变更原因
    ↓
判断归档位置：
  - 需求文件夹文档 → 00-项目管理/[项目名]/[需求编号-需求名称]/
  - 项目主文档 → 00-项目管理/[项目名]/[文档类型]v1.0.md
    ↓
更新项目 CHANGELOG.md
    ↓
手动 push 到 GitHub
    ↓
思月向银月汇报归档结果
```

> **注意**：如音移建的文档由如音负责内容质量，思月仅做归档格式审查。如有内容问题应退回如音修正。

### 3.2 紫灵移交（思月接收）

```
紫灵完成需求文档
    ↓
提供变更摘要：
  - 需求编号
  - 需求名称
  - 变更摘要（一句话）
  - 变更原因
    ↓
思月在对应项目目录下创建 [需求编号-需求名称] 文件夹
    ↓
归档需求文档及关联文档
    ↓
更新项目 CHANGELOG.md
    ↓
手动 push 到 GitHub
    ↓
思月向银月汇报归档结果
```

### 3.3 文档合并（银月/老大主动发起）

```
银月/老大说：「合并xxx需求文档」
    ↓
思月将需求文件夹下的文档合并到项目主文档
    ↓
在变更记录中新增：
  ## [版本] - [日期]（合并自《需求编号-需求名称》）
    ↓
更新项目 CHANGELOG.md
    ↓
手动 push 到 GitHub
```

### 3.4 群内 @ 接收机制

当文档编写者在飞书群中 @ 思月并发送文档时，思月按以下流程处理：

```
收到群内 @ 消息
    ↓
确认文档内容和来源：
  - 如音移交 → 按 3.1 处理
  - 紫灵移交 → 按 3.2 处理
  - 其他来源 → 判断归档位置或暂存 04-临时/
    ↓
归档（新增或版本更新）
    ↓
版本更新时审查更新要素：
  - 变更摘要、变更原因、版本号、日期
  - 缺失要素由思月代为补全
    ↓
手动 push 到 GitHub
    ↓
在群内回复归档结果
```

## 5. Obsidian 使用规范

1. **不要删除或移动 .obsidian 目录**（插件配置目录）
2. **不要删除或移动 .git 和 .gitignore**（版本控制目录）
3. **大型二进制文件不要放入 Vault**（会导致 Git 仓库膨胀）
4. **完成变更后必须手动 push 到 GitHub**（保持双端同步）
5. **手动 pull/push 同步**（PC/手机端每次编辑前先 pull，完成后 push）
6. **commit 信息格式**：`feat: [简短描述]` / `fix: [简短描述]`
7. **wikilink 使用**：Obsidian 支持 `[[文档名]]` 链接，推荐使用

## 6. 零散文档处理

- **来源**：未通过正式归档流程的零散文档，集中存放在 `04-临时/`
- **处理方式**：定期审阅，确认归属后正式归档，或清理删除
- **迁移记录**：已本次处理，`hermes-workspace/docs/` 等零散文档已迁入 `04-临时/`
